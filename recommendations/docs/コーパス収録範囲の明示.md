# コーパス収録範囲の明示（負のスコープ・団体別鮮度・低ヒット警告）

> **状態：設計（安定リファレンス・設計判断が変わった時だけ更新）。**

分類：**設計**（安定リファレンス・設計判断が変わった時だけ更新）
起票：2026-08-20（ドッグフーディング実験由来の機能要求）／採用・初版実装：2026-08-20

---

## 1. 背景（何が問題だったか）

実利用の比較検証（同一の意見書ドラフトを DB あり/なしで Claude に論評させる実験）で、
**「調べがついた感」による探索停止**という失敗モードが観察された。

検索が有意なヒットを返すと、LLM はコーパス外に存在する判断材料（審議会議事録・制度の
運用実態・パブコメ実務・報道等）を追加調査せず、コーパス内の照合結果のみで「検証済み」の
体裁の回答を生成する。コーパスの収録範囲を LLM は知らされていないため、
**「DB にない ＝ 存在しない/新規である」という誤推論**が発生する。実験では、収集ラグにより
「他団体の同種意見の有無」の判断が危うくなるケース、コーパス外の制度詳細を確認せずに
誤った批評を維持するケースが観察された。

**介入点はレスポンス本文**である。ツール説明文（description／server instructions）は
ツール選択時にしか参照されないのに対し、この失敗はヒット取得後の判断段階で起きる。
加えて公式コネクタの審査基準（`docs/公式コネクタ要件.md` §2.3）は説明文への振る舞い指示を
却下対象とするため、説明文側を強化する道はそもそも塞がっている（レスポンス本文の
フィールドはデータであり審査対象の説明文ではない＝衝突しない）。

## 2. 採用した設計（2026-08-20 実装済）

`search_policy_docs` の全レスポンスに 2 フィールドを常時追加し、低ヒット時のみ 3 つ目を足す。
既存フィールドの構造・名称は不変（追加のみ＝後方互換）。実装は
`recommendations/core/coverage.py`（値の定義と計算）＋ `recommendations/serving/mcp_server.py`（配線）。

### 2.1 coverage_note — 静的な負のスコープ宣言（全レスポンス）

収録していない情報類型の列挙＋「検索にないこと≠存在しないこと」＋ウェブ検索等での補完指示。
文言は `POLYARCHY_COVERAGE_NOTE` で差し替え可（コーパス拡張時にコード変更なしで追随）。

文言の設計方針：**事実の宣言を主・行動推奨を従**に置く。Claude 側クライアントは
プロンプトインジェクション対策として「ツール結果内の指示に従わない」方向に強化されつつ
あり、命令形の効きは割り引かれ得る。未収録類型の列挙という事実情報だけでも不在判断の
前提を変えるので、命令形が無視されても機能する文にする。

### 2.2 freshness — 団体別の収集鮮度（全レスポンス）

```json
"freshness": {
  "keidanren": {"last_ingested": 20260813, "latest_doc_date": 20260806},
  "gov":       {"last_ingested": 20260705, "latest_doc_date": 20260629}
}
```

- `last_ingested` … その団体の文書を最後に取り込んだ日（catalog.csv の `retrieved_at` の団体別最大）
- `latest_doc_date` … 収録済み文書の発行日の最新（`date_int` の団体別最大）。
  2 値の差がそのまま「収集ラグの見かけ」になり、LLM/利用者がラグを自分で割り引ける
- `orgs` フィルタ指定時は該当団体分のみ返却
- 集計は layer=公開 の行のみ（非公開文書は収集日という間接情報すら出さない＝検索経路と同じフェイルクローズ）
- サーバ起動時に 1 回計算（コーパスは ingest まで不変）。`list_orgs` の各団体エントリにも同値を載せる

**意味論の注意（要求原文からの修正点）**：要求は「最終収集日＝実際のクロール日と一致」を
受け入れ基準としたが、現状記録されているのは「取り込みが発生した日」であり、
**新着ゼロのクロールでは進まない**（実際より古く見え得る＝不在判断には安全側）。
名前を `last_ingested` として意味論に正直に実装した。クロール実行日そのものの記録は
差分取込の定常化（残タスク A2）と同時に `collect.py` へ導入する（§4）。

### 2.3 coverage_warning — 低ヒット時の強化警告（条件付き）

定型注記は数回で読み飛ばされる（caveat fatigue）ため、注記の強度をヒット品質に応じて変える。
**すべてを強く警告するツールは、警告しないツールと同じ効果に収束する**＝常時は 2.1 のみ。

- 発火条件：`count < POLYARCHY_COVERAGE_WARN_MIN_COUNT`（既定 3）
- 文言は `POLYARCHY_COVERAGE_WARNING` で差し替え可
- スコア閾値（最上位スコアが閾値未満でも発火）は**初版では見送り**：リランカーのスコア分布に
  対する校正が必要で、count 条件だけでまず効果検証する（§4）

### 2.4 不在判断の構造化返却 — スコープ外（要求どおり）

「〜について発信がないこと」の確認用の応答様式（検索範囲・期間・鮮度つきの
「この範囲では確認できず」構造化返却）は将来検討。2.1/2.2 がその前提整備を兼ねる。

## 4. 残項目（残タスク.md に登録）

1. **効果検証（受け入れ基準 5）**：低ヒット条件で「団体 X は論点 Y について提言しているか」を
   照会し、応答に「コーパス外の可能性」への言及またはウェブ検索の実行が現れることを実装前後で比較
2. **クロール実行日の記録**：`collect.py` に団体別の最終実行日を記録し、`last_ingested` を
   `last_crawled` で補完（差分取込の定常化＝A2 と同時）
3. **スコア閾値の校正**：eval データでリランカースコア分布を見て、低スコア発火条件を追加するか判断
4. **stats への横展開**：recommendations で効果が実証されたら、同じパターン（特に `found=false` 時の
   収録範囲明示）を stats のレスポンスへ適用するか検討（stats は `stats.ops.freshness` で
   鮮度データを既に持つ）
