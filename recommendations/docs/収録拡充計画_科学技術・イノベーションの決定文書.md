# 収録拡充計画：科学技術・イノベーションと防衛・デュアルユースの決定文書（gov への追加）

> **状態：設計（2026-11-14 起案）。** 評価問・収集器・説明文の変更を 1 つの変更で行う（ルート CLAUDE.md §6）。取込は運用側（配布用のクローン・RUNBOOK §5）。
> 持つもの＝対象文書・取得の作法・評価問・影響・手順。持たないもの＝進捗（[残タスク](../../docs/残タスク.md) B51）・基準値（ルート README「品質の担保」）・会議の回ごとの資料と議事録（審議会議事録DB＝[第 4 便の計画](../../deliberations/docs/第4便_計画.md)）。
> 型は [収録拡充計画：AI・デジタル改革の決定文書](収録拡充計画_AI・デジタル改革の決定文書.md)（B26・B27・B29・B31）と同じ。

## 0. 要約

- **発端**：導入団体の利用者から、科学技術・イノベーション政策と、防衛・デュアルユースの産業政策の文書を引きたいという要望（2026-11）。欲しいのは**まず決まった中身**（計画・戦略・方針・取りまとめ）、無ければ議論の過程。期間は 2024 年以降。
- いまの `gov` では、防衛・デュアルユースや AI for Science は骨太方針・日本成長戦略などの**中の記述**としてしか当たらない。科学技術政策の決定文書そのものは入っていない。
- **住所**：決まった中身は本 DB の `gov`（この計画）。会議の回ごとの資料と議事録は審議会議事録DB（第 4 便）。公募要領・採択結果・事業の成果報告は入れない（施策の運用の情報で、方針ではない）。
- **第 1 便＝9 系統・31 本**。あわせて、ツールの説明文から `gov` の系統の列挙を外す（§5.1・1 回きり）。

### 1.1 決定日の読み方（収集器）

- 掲載ページに決定日が書かれている系統は、ページから読む：`kihon`（閣議案件のリンクの和暦）・`togo`（一覧のリンクの「（YYYY年M月D日閣議決定）」）・`moonshot`（リンクの「（決定主体、令和…決定）」）・`inno`（一覧のリンクの「YYYY年M月D日 中間とりまとめ」）。
- 書かれていない系統（`kprog`・`gsc`・`sip`・`bridge`・`aifors`）は、表紙の決定日（改正のあるものは最後の改正の日）を `collect.py` の `PINNED_GOV` に持ち、掲載ページにそのリンクがあることを毎回確かめる（無ければ止める＝移転・差し替え）。
- **新しい 9 系統はどれも、取った PDF の 1 頁目に決定日が載り、それより後の日付が載っていないことを確かめる**（`_cover_date_ok`）。同じファイル名のまま改正版に差し替わったら、その文書は `error` になり取り込まれない＝表を直す合図。
- `inno` の題は報告のページの `<title>` から取る（分科会の名前が年で違う＝2024 年版は産業技術環境分科会・2025 年版から イノベーション・環境分科会）。本文の PDF のリンクも年で書き方が違う（2026 年版は「…中間とりまとめ（PDF形式：…）」1 本・2024・2025 年版は「…中間とりまとめ（本文）（PDF形式：…）」と概要・参考資料が並ぶ）＝両方を拾い、ちょうど 1 本のときだけ採る（0 本・2 本以上は `html_only` で catalog に残る）。

## 2. 取得の作法

- 内閣府（www8.cao.go.jp）・文部科学省（www.mext.go.jp）：既存のとおり（この名乗り・1.5 秒の間隔）。2026-11-14 に両方とも 200。
- **経済産業省（www.meti.go.jp）**：UA の文字列で弾く（この名乗りに 403）＝ブラウザの名乗りで取る（`collect.py` の `HOST_RULES`）。**続けて取ると AWS WAF の JS チャレンジ**（HTTP 202・`x-amzn-waf-action`・本文なし）＝**解かない**。前の要求から 120 秒あけ、チャレンジが出たら `WafChallenge` でそのホストへの要求をその実行の間は送らない → 時間をおいて `--skip-existing` で続きから。2026-11-14 は 120 秒おきで一覧 1・報告のページ 3・PDF 3 の 7 本がチャレンジなしで通った。
- 取込で要る経済産業省への要求は計 7 本（一覧・報告のページ 3・PDF 3）。**`inno` は最後に単独で**（`--source inno`）。目次が取れない系統があっても、ほかの系統の収集は続き、最後に「目次が取れなかった系統」として出る。
- 新着の確認（箱の `check_new`・毎日）は経済産業省の一覧を 1 本だけ取る（報告のページと PDF は取込のときだけ）。1 系統が取れなくても、ほかの系統の新着は数え、行は「チェック失敗（目次が取れない系統: …）」になる（`source_errors` に系統ごとの理由）。

## 5. 影響

### 5.1 ツールの説明文から系統の列挙を外す（1 回きり・ChatGPT のコネクタの作り直し 1 回）

- 今までは `gov` の系統の名前が、**サーバの説明（`SERVER_INSTRUCTIONS`）とツールの説明（`search_policy_docs` の docstring）の両方に列挙されていた**＝系統を足すたびにツールの定義が変わり、ChatGPT のコネクタを作り直していた（B26・B27・B29・B31）。
- この便で列挙を「閣議決定・会議決定・審議会の答申など主要な方針文書。系統の一覧は返り値の coverage_note と list_orgs」に変えた。`coverage_note`（`core/coverage.py`）と `list_orgs` の名称（`core/orgs.py`）は定義の外＝今までどおり正確に列挙する。**以後は `gov` に系統を足しても作り直さずに済む。** 件数（約 3,700 文書／約 187,000 チャンク）は据え置き。
- 審議会議事録DB の同じ変更（会議体の列挙を外す）も同じ変更に入れた＝ツールの定義の記録（`polyarchy_common/tests/tool_definitions/`）は recommendations と deliberations の 2 つが変わる。**配布の後、ChatGPT のコネクタは両方まとめて 1 回作り直す。**

### 5.2 収集器の直し（既存の系統にも効く）

- 本文の無かった行（`html_only`・`error`）の分野タグは題名だけの判定＝本文が取れて索引に入る行へは持ち越さない（`write_catalog`）。追い判定の既定の対象は索引に入る行（`ok`・`html_text`）だけ（`policy_tagger`）。取込は catalog のタグを payload に写すので、直さないと題名だけのタグが索引に入る。

### 5.3 箱

- 31 本・数千チャンクの追加（全体の 1〜3%）。政策主張DB のメモリはモデルが大半＝影響は小さい。
