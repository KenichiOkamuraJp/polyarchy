# 運用モデルと事業継続性 — なぜこの形なら依存しなくて済むのか

> **状態：設計（安定リファレンス・導入を検討する団体への説明用）。** 起草 2026-09-03・2026-09-04 全面改訂（全部公開前提）・2026-09-19 改訂（特定の当事者を前提にした記述を除いた）。
> 宛先＝導入を検討する団体の関係者、特にシステム担当。本ソフトウェアの運用モデルが**特定の開発者・事業者の善意ではなく構造で**
> 担保されていること、そして**誰にも依存しなくて済む形**になっていることを説明する 1 枚。

## 0. 大前提：この製品の「業務有効性」はまだ検証されていない

本書の主張はすべて**「仕事の役に立つなら」という条件付き**です。本ソフトウェアが実際の業務（提言の作成・政策の比較・
統計の確認）に有効かどうかは、まだ十分に検証されていません。これまでの試行は少人数・短期間であり、
**本格的な検証は、導入する団体それぞれの現場で行うもの**です。

だから設計の出発点は「役に立たなければ止められること」です。止めたとき何も残らない負債（名義・契約上の縛り・属人知識）が
無いように作ってあります。**有効でなければ止める。止めるための手順と条件は §4 に置きます。**

役に立つと分かった場合に受け取れるものは、いわゆる SaaS のメリットです：収録データの更新、利用者の質問から改善が回る仕組み、
運用の自動化。ただし一般の SaaS が抱える欠点——中身が見えない・囲い込まれる・やめると何も残らない——は無い。
**一言で言えば「ソースが公開された SaaS」**です。

## 1. 前提の見極め：保守ニーズは消えない。AI が消すのは「作業」であって「責任」ではない

AI ツールが作業を強力に支援する時代でも、「動いているか誰が見るのか」「壊れたら誰が直すのか」
「更新しても大丈夫だと誰が保証するのか」——**責任の引き受け手**は必要であり続けます。

本サービスではこの分離を実装しています：**作業は自動化**（毎時の稼働監視・毎日の更新チェック・
品質検査に全合格したときだけ配布される仕組み・サーバへの無人適用・失敗時の自動切り戻し）、
**責任は導入団体側の担当者が負える形**（すべての操作が記録に残り、担当者が独立に検証でき、定型作業は担当者へ移す）。
上流（公開リポジトリの保守者）は、導入団体の運用の責任主体ではありません。

## 2. 従来の保守外注と、この運用モデルの違い

システム保守の外注で不信が生まれやすい連鎖は「ソース非開示 → 属人化 → 監査不能 → 抜けられないから続ける → 割高感」です。
本モデルは各項を逆にする設計です（比較は一般論であり、特定のベンダーや現行契約を評価するものではありません）。

| | 従来の保守外注 | 本モデル |
|---|---|---|
| ソースコード | 非開示（引き継ぎ不能） | **全部公開（オープンソース）**＝コード・運用自動化・評価資産・設計文書まで。導入団体に限らず誰でも引き継げる |
| システムの名義 | ベンダー名義・ベンダー環境 | **導入団体名義**（AWS・Cloudflare・認証基盤すべて） |
| 構築・運用を担う人の操作 | 見えない | **操作が記録に残り、操作した本人には消せない**（AWS CloudTrail＝管理操作 90 日・データ配布 400 日／git 履歴。導入団体が管理者権限を持つ限り） |
| 品質 | 「信じてください」 | **出荷ごとに検査数値が刻まれる**（品質検査に全合格したものだけが配布される）。検査は公開リポジトリと CI で誰でも再現できる（CI 化は計画＝[運用設計](運用設計.md) §2.5） |
| 更新作業 | 人手＝ミスも属人性も混入 | **無人・自動**（人手のサーバ操作ゼロが定常）。更新の実行役は導入団体側の担当者が担える |
| 続ける理由 | 抜けられないから | **役に立つ間だけ**。役に立たなくなったら止める。止めても手元に残る |

要点は最後の行です。**出て行くコストがゼロで、続けるかは有効性だけで決められる**——それが健全な形だと考えています。

## 3. 事業継続性は「構造」で担保する

**導入団体側の保険（開発者・保守者に何かあっても困らない）**
- ソース・文書・データ・評価セット・自動化の仕組みがすべて公開され、引き継ぎ可能な形で残る（属人知識に依存しない
  ことを、文書と監査で確認できる）。
- インフラは導入団体名義＝アクセス権の付与も剥奪も導入団体がいつでも行える。
- 運用は「非開発者でも回る」ことを目標に自動化されている（1 コマンドの更新・失敗時は何も配布されない・適用に失敗したら旧版へ自動復帰）。
  定型更新の実行役（運用者）・障害対応者を非開発者が担うための条件と手順は [運用設計](運用設計.md) §0。

**上流の事情に左右されない構造**
- 本ソフトウェアはオープンソースとして公開されているため、上流の保守者の事情（離脱・不測）に関わらず誰でも利用できる。
  改良が続くかどうかは上流の状況と需要によるが、**続かなくても導入団体の運用は止まらない**（更新サイクルは導入団体側で回る）。

**共有される改良資産**
- 利用から得られる改善のサイクル（どんな検索が失敗したか→収録と検索品質の改善）は、利用者を識別できない
  形の評価資産として公開リポジトリ内に蓄積される＝**導入団体側の開発者も使える共有資産**。
  導入団体はこの還元に**協力できる（義務ではない）**。

## 4. 検証のすすめ（検証期間と終了条件）

本書の主張はすべて検証可能です。[監査ガイド](導入団体側_監査ガイド.md)の手順で、ソースと文書の一致・
稼働状態・操作履歴・品質数値を、導入団体側の担当者がご自身のアカウントと AI ツールで独立に
確認できます。**信頼してくださいではなく、確認してください**——それがこの運用モデルの立脚点です。

業務有効性の判定は次の形で行うことを勧めます：

- **検証期間**＝導入後 3 か月。
- **判断材料**＝週次利用レポートの数字（利用者数・件数・0 件率）と、実際の業務で役に立った質問と立たなかった質問の数。
- **判断**＝継続か縮退か。縮退＝サーバ停止（費用ゼロ・データは導入団体の手元に残る）。判断は導入団体が行う。
