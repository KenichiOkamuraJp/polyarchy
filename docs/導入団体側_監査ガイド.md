# 導入団体側 監査ガイド — システム担当が自身のアカウントで全リソースを検証する

> **状態：正典（実務ガイド・導入団体のシステム担当が使う）。** 起案 2026-09-03・2026-09-04 改訂（公開リポジトリと CI で誰でも再現できる形へ）・2026-09-19 改訂（特定の当事者を前提にした記述を除いた）。
> 用語と役割の定義＝[用語と役割.md](用語と役割.md)。
> 目的＝**構築・運用を担う人（デプロイ担当・運用者。外部の人でも内部の人でも）を信用する必要がない形**をつくる：導入団体側の担当者が、自分のアカウント・自分の
> Claude Code で、ソースコード・AWS リソース・稼働状態のすべてを**独立に監査できる**ことを担保する。
> ソースコード・文書・品質検査は**公開リポジトリと CI で誰でも再現できる**＝監査は指定担当者に限らない。
> これはアカウント所有の原則の帰結（導入団体名義のリソース＝導入団体が常に全権を持つ）。

## 0. 前提となる2つの事実（監査の土台）

1. **デプロイ担当・運用者の導入団体 AWS 上の操作は自動的に記録される**：2 段構え＝**管理操作**（EC2・IAM・SSM・鍵の発行等）は
   AWS CloudTrail の既定イベント履歴（**90 日**）、**データ配布操作**（S3 `data/`・`release/`・`code/` への書込 1 件 1 件・実行者 ID 付き）は
   専用証跡（terraform `trail.tf`・**400 日**）。**操作した本人が自分の操作記録を消すことはできない**（導入団体が管理者権限を持つ限り）。
2. **複製後のコードの全履歴は導入団体のリポジトリに残る**：複製以降の全コミットが作成者・日時つきで残り、
   マイルストーンはタグ・リリース（例 `prod-ready-YYYY-MM-DD`）で固定できる。履歴の改竄は
   force-push を要し、それも GitHub 上で検知可能。なお上流の公開リポジトリは初期開発の履歴を含まない
   （最初のコミットがその時点のスナップショット）。

## 1. 担当者側で用意するもの

| 対象 | 付与するアクセス | 手順 |
|---|---|---|
| **AWS（導入団体アカウント）** | **ReadOnlyAccess**（推奨＝監査は読取専用が安全。管理者権限は導入団体の判断で） | IAM Identity Center（または IAM）で担当者自身のユーザーを作成し、AWS 管理ポリシー `ReadOnlyAccess` を付与 |
| **GitHub リポジトリ** | 不要 | 公開リポジトリは誰でも clone できる。導入団体が複製した自組織のリポジトリは、自組織の権限設定で Read を付与 |
| **Claude Code** | — | 担当者自身の Claude 有料プラン（Pro 以上）。組織のポリシーに従い自身の端末にインストール |

★読取専用（ReadOnlyAccess）の意味：**Claude Code に何を指示しても、AWS 側は一切変更できない**。
AI を使った監査で「誤って壊す」リスクが権限側で構造的に消える。

## 2. Claude Code でできる監査（例）

リポジトリを clone して Claude Code を開き、たとえば次のように指示する：

- **文書とコードの突合**：「README とリンク先の文書に書かれた仕様・数値が、ソースコードの実装と一致するか
  監査して。不一致をファイル名と行番号つきで列挙して」
- **セキュリティ観点**：「このコードベースに、外部送信・書き込み・非公開データへのアクセス経路がないか
  確認して。層（公開/機密）の分離がどこで担保されているか示して」
- **品質ゲートの実走**（ルート README「品質の担保」のコマンドをそのまま）：stats の4ゲートと共通契約テストは
  ローカルで完結する。recommendations の検索ゲートは検索データ・モデルの取得が要るため、現状は箱上での実行
  （§3・要 SSM 権限）が現実的＝**この 1 点だけは ReadOnly 権限では独立実走できない**（限界として明示。出荷時の数値はマニフェストとダッシュボード②で確認できる）。
  **CI 化（計画＝[運用設計](運用設計.md) §2.5）後は、全ゲートが公開リポジトリの CI（GitHub Actions）で PR／main ごとに走り、結果は誰でも見られる**＝この限界は解消する。
- **AWS の実状態**（ReadOnly の profile で）：「aws CLI でこのアカウントの EC2・S3・SSM パラメータ一覧・
  CloudWatch アラームの構成を調べ、deploy/ 配下の Terraform 定義・手順書と一致するか確認して」
- **操作履歴**：「CloudTrail のイベント履歴から、直近の操作を操作者別に要約して」
- **稼働の外形検証**（AWS 権限すら不要・curl のみ）：`deploy/PROD_MIGRATION.md` §5.2 の手順どおり
  healthz 200／既定パス 403／PRM 配信／未認証 401 を確認する。

## 3. 読取専用に収まらない監査（必要時のみ）

箱（EC2）のシェルに入っての監査（SSM Session Manager）は「読取専用」の枠を超える（シェルは何でもできる）。
必要な場合は：(a) 導入団体の判断で担当者に SSM セッション権限を付与する（Session Manager は**セッション内の
全操作をログに残す設定**が可能）、または (b) 運用者・障害対応者の作業に画面同席する。日常の監査は §2 で足りる想定。

## 4. 定常的に見える化されているもの（監査を待たずに届く）

- **運用ダッシュボード**：S3 `ops/dashboard/index.html`（**毎時自動更新**）＝①稼働（ユニット・healthz・ディスク）②バージョン・規模
  （コード版・データ版＝released/applied・出荷時の検査数値・smoke）③データ鮮度（団体別最終取込・新着・統計取得元の変化）④利用（直近 4 週の件数）
  の 4 区画が 1 枚で見える（companies を有効にした環境では①にユニットと healthz、②に収録社数の行が加わる）。**日常の状態確認はこれで完結**し、シェルに入る必要がない（§3 の場面を最終手段に限定）。
- **更新チェック**：毎日自動で「提言の新着・統計取得元の変化」を検出しダッシュボードに表示。**手動で今すぐ
  チェックしたいとき**は AWS コンソール → Systems Manager → Run Command → `polyarchy-<env>-check-updates` を
  選んで実行（＝ボタン。チェックのみで取込はしない・実行記録は CloudTrail に残る。実行には ReadOnly を超える
  権限〔このドキュメント限定の ssm:SendCommand〕が要る＝付与は導入団体の判断）。
- **週次利用レポート**：S3 `ops/report/`（数字のみ・検索語なし）＝導入団体アカウント内なので担当者が直接閲覧可。
- **アラームメール**：SNS 購読に担当者のメールアドレスを追加すれば、障害・異常は運用者と同時に受信する
  （`deploy/env/prod.env` の `ALERT_EMAIL`／SNS 購読の追加）。
- **利用ログは30日で自動削除**：削除はサーバのタイマーと S3 ライフサイクルの両方で機械的に担保
  （設定は Terraform 定義＝リポジトリ内で監査可能）。

## 4b. データ更新の監査線（2026-09-03・人手の箱操作ゼロ設計）

データ更新は「ローカルで製作・ゲート全 PASS → S3 へ配布＋マニフェスト → 箱が 15 分毎に自動適用」の一方通行。
- **運用者の日常権限は S3 の `data/`・`release/`・`code/` 書き込み＋`ops/` 読み取りのみ**（定義＝deploy/iam-data-operator-policy.json・箱に触れない・捕捉ログは読めない）。
- upload は CloudTrail データイベントに、箱の適用は journal→CloudWatch に、それぞれ機械的に記録される。
- マニフェスト（`release/data.json`）には**出荷時のゲート数値**が入り、ダッシュボード②で released/applied の
  一致と適用後 smoke の PASS/FAIL が見える＝「何がいつどの品質で反映されたか」を担当者が独立に検証できる。
- 箱の適用ログは CloudWatch Logs `polyarchy/dataapply`（退避→コード反映→同期→smoke→判定）に残る＝適用の一部始終を
  ReadOnly で読める。**smoke FAIL 時は自動で旧版へ切り戻し**（2026-09-03）＝壊れたリリースは配信されず、
  ダッシュボード②に「ROLLED_BACK／旧版で稼働中」と出る・アラーム `dataapply-rollback` がメールで届く。
- SSM シェル・Run Command 等の管理系は障害対応の非常口のみ（§3）。

## 5. この仕組み自体の位置づけ

契約ではなく**運用上の担保**。思想＝「導入団体名義のリソースは導入団体のもの・構築や運用を担う人は、許可された作業者にすぎない」。
逆方向も対称で、開発者の検証環境（staging）・個人アカウントは監査対象外（そこに導入団体のデータは存在しない＝導入団体のデータは
導入団体の環境内に留める設計）。突合先＝公開リポジトリ＝文書・コード・品質検査の正典はそこにある。
