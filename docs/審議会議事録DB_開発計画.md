## 0. 要約

- **何を**：政府の会議体の**過程文書**（回ごとの配布資料・議事録・議事要旨・議事概要）を検索する 2 つ目の文書検索サービス。決定文書は政策主張DB の `gov` に入れ、ここには入れない。
- **最初の範囲**：AI・デジタル関係の会議体。第 1 便はデジタル行財政改革会議（本会議）・人工知能戦略本部と専門調査会・AI 戦略会議の約 320 文書。議事の記録の 3 つの型（逐語・名前つき要約・匿名要約）がすべて入る組み合わせにした。
- **初手**：検索エンジンの部品を共有パッケージ（仮称 `polyarchy_retrieval`）へ切り出す。政策主張DB の上位 k 件の並びが変わらないことを機械で確認できるようにしてから行う。
- **芯の約束**：返す断片には毎回「会議体・回次・資料番号・提出者区分（または発言者）」を付ける。**民間議員・有識者・外部団体の資料を政府の立場として読ませない**のが、このサービスを分けた理由。提出者・発言者は推定で埋めない（分からなければ「不明」）。
- **箱**：開発とゲートは手元で完結する。箱に載せるかどうかは既存プロセスのメモリを実測してから決める。

## 1. なぜ政策主張DB と分けるか

### 1.1 発端（2026-10-02）

デジタル行財政改革会議が第 14 回（2026-07-07）で「AI・デジタル改革推進会議」への改組を決めた。新会議を中心に、人工知能戦略本部・規制改革推進会議と AI の法制度・ガイドラインを見直すとされている。この議論を追えるデータを検討したところ、追いたいものが 2 種類あった。決定された内容（取りまとめ・基本計画）と、そこに至る議論（大臣・構成員・各省・ヒアリング先が回ごとに出した資料と発言）である。

### 1.2 検討した案

| 案 | 内容 | 判断 |
|---|---|---|
| A | 会議資料・議事録も政策主張DB の `gov` に入れ、`doc_type=資料／議事録` で区別する | **採らない** |
| B | 決定文書は政策主張DB、過程文書は新しいDB（**採用**） | 採用 |
| C | 会議体ごとに DB を分ける | 採らない（[長期開発計画](長期開発計画.md) §8 で却下済み＝ファセットで足りる） |

**A を採らない理由（[長期開発計画](長期開発計画.md) §2 の 4 軸を実データに当てた結果）**

- **引用の主体が違う。** 第 14 回の資料は「資料１ デジタル行財政改革担当大臣提出資料」「資料９ ○○構成員資料」と並ぶ。規制改革 WG では「資料１ 一般社団法人日本経済団体連合会提出資料」「資料５ 法務省提出資料」が同じ回に並ぶ。政策主張DB の断片は「機関の立場」を代表するので、ここに構成員の個人資料が混ざると、利用者の LLM が「政府は〜としている」と書く誤りの温床になる。政策主張DB はすでに `doc_type=資料`（経団連のアンケート結果など）で同じ種類の注意書きを serverInstructions に持っている。これ以上増やすと、説明文で防ぐ限界を超える。
- **チャンクの単位が違う。** 決定文書は意味段落で切る。議事録は 1 発言、スライドは 1 ページが自然な単位になる（§4）。
- **メタデータが違う。** 政策主張DB の芯は団体・分野・日付。こちらは会議体・回次・資料番号・提出者区分・発言者。
- **評価が汚れる。** 政策主張DB のアンカーは「主張文書の検索」を測っている。同じ語を含む議事録が大量に入ると、既存の正解が上位 5 件から押し出され、測りたいものが変わる。

**B の具体化**：同じ会議体の文書を 2 つの DB に分ける（住所を決めるのはジャンル）。決定文書の取り込みは [収録拡充計画](../recommendations/docs/収録拡充計画_AI・デジタル改革の決定文書.md)（[残タスク](残タスク.md) B26）で先に進める。

## 2. 検索エンジンをどこに置くか

### 2.1 問題

ハイブリッド検索（BM25＋ベクトル→融合→リランカー）と Qdrant まわりは `recommendations/core/` にある。規約は「サービスは互いのソースを読まない（共有は `polyarchy_common` だけ）」。一方で [長期開発計画](長期開発計画.md) §3（2026-10-02 改訂前）は「検索スタック・設定・評価はコーパス固有」としていた。2 つ目の文書検索コーパスを作る時点で、この食い違いを解く必要がある。

### 2.2 検討した案

| 案 | 内容 | 判断と理由 |
|---|---|---|
| ① | `deliberations` が `recommendations.core` を import する | **不可**。規約違反。審議会側のセッションが政策主張DB のソースを読むことになり、把握範囲が閉じない |
| ② | 部品を `deliberations/` に**複製**する | **次点**。政策主張DB の経路に一切触れないのが利点。ただしモデルの版の固定・読み込みの地雷（§2.4 のキャッシュ先の食い違いなど）が 2 か所に分かれ、片方だけ直る |
| ③ | コーパスに依存しない部品を**共有パッケージ**に切り出す | **採用**（[長期開発計画](長期開発計画.md) §3 を 2026-10-02 に改訂） |
| ④ | ③を残タスク D「検索コアのコレクション引数化」（同種コーパスの複数コレクションを融合する能力）と一体で作る | **採らない**。D は「同種のコーパスなら分割されていても一発で横断できる」能力で、D 自身が異種コーパスの横断マージを禁じている。着手条件（非公開層を持つ導入案件）も満たされていない。審議会DB に要るのは「1 サービス＝1 コレクション」をコレクション名の引数で扱うところまで |

**③の置き場所を `polyarchy_common` にしない理由**：統計参照DB だけを載せる箱は `pip install -e ".[stats]"` で torch を引かない。検索部品は torch・sentence-transformers を引く。同じパッケージに入れると、この依存の分離が崩れる。

### 2.3 何を共有し、何を残すか（2026-10-02 のコード調査）

| 区分 | 部品（現在の場所） | 扱い |
|---|---|---|
| **そのまま共有** | `tokenize_ja`（fugashi のシングルトン）・`rrf_fuse`・`BM25Index`（`core/hybrid.py`）／CrossEncoder の読み込み・`RERANKERS`（`core/rerankers.py`）／`_hf`・`EMBEDDING_MODELS`（`core/embeddings.py`）／`interleave_unique`（`core/multiquery.py`）／`QdrantCorpusStore`（`core/qdrant_store.py`） | 移す |
| **引数化して共有** | `build_sparse_bm25`・`QdrantBM25`（コレクション名・語彙の置き場・フィルタ変換を引数に）／`ensure_collection`（絞り込み用の索引を引数に。**`layer` は必須で残す**）／ベクトルの次元（768 は ruri 前提）／`HybridRetriever`（下記 4 点） | 移す |
| **作り直し** | フィルタ（`SearchFilter`・`qdrant_filter` は org・layer・date_int と分野の述語に固定）→ 共有側は「Qdrant の Filter を受け取り、`layer` 条件が無ければ拒む」器だけを持つ | 器だけ共有。意味は各コーパス |
| **固有のまま** | `config`（調整値）・`SearchFilter` の意味・`orgs`・比較型の分解（`detect_comparative_orgs`）・`multistage`・`coverage`・`search_api` の返り値の型・`query_capture` | 残す |

**`HybridRetriever` で引数にする 4 点**：(a) 候補を広げる倍率と厳密検索の可否（いまは config からの遅延 import）、(b) クエリをフィルタの変種に分ける関数（いまは政策主張DB の比較型分解が埋め込まれている）、(c) フィルタを Qdrant の Filter に変える処理と後段の述語、(d) 起動時に全チャンクの本文とメタデータを読み込む辞書（政策主張DB では 18.7 万チャンク分がメモリに載る）。

**切り出しで同時に解く地雷**
- `config` は import した時点で `load_dotenv()` を呼び、`VECTOR_BACKEND` が qdrant 以外なら例外を投げる。**共有部品は `config` を import しない**（値は引数で受ける）。
- 箱では `COLLECTION_NAME` が全ユニット共通の `deploy.env` にある。新サービスが同じ名前の env を読むと `policy_claims_v7` を拾う。**審議会DB は別名の env（例 `DELIB_COLLECTION`）か引数で渡す。**
- Qdrant の `CORPUS_REGISTRY` は書き換えのできる dict で、評価コードが直接書き換えている。共有側に移すなら、登録の口を関数にする。

### 2.4 llama_index と埋め込みの扱い

- 検索側（融合・リランク）は ID 列・本文列・スコア列の入出力で書ける。**共有部品に llama_index は持ち込まない**（`BaseRetriever`・`BaseNodePostprocessor` の包装は政策主張DB 側に残す）。
- 埋め込みだけは慎重に扱う。現在は llama_index の `HuggingFaceEmbedding` が SentenceTransformer をプレフィックス（「検索クエリ: 」「検索文書: 」）・正規化・バッチ 10 で包んでいる。直接呼ぶ形に置き換えるとベクトルが変わり得る。**第 1 段は `HuggingFaceEmbedding` をそのまま使う**（ベクトルの同一性を保証する）。置き換えは、同一性を確かめる道具（§2.5）ができてから別の変更で行う。
- 調査の副産物：ruri の重みのキャッシュ先が、事前ダウンロード（`HF_HOME`）と実行時（llama_index 独自のキャッシュ）で食い違っている疑いがある。箱では初回起動のたびに再ダウンロードしている可能性がある。モデルの読み込みを 1 か所にまとめる機会なので、別の作業として確認する（直すならベクトル不変の確認つき）。

### 2.5 「並びが不変」をどう確かめるか

- 現状の評価は hit@k と MRR を集計して表示するだけで、**問ごとの上位 k 件を保存していない**（`eval/full.py` は保存するが、経路が本番と違い、API クレジットも使う）。
- **最小の追加**：`recommendations/eval/retrieval.py` の `retrieve_top`（すべての問の種類が通る 1 か所）で `{問ID: [file_name…]}` を集め、`--dump-topk PATH` で JSON に書く。フィルタの評価（`eval/filters.py`）も同じ形で書き出す。
- 切り出しの前後で同じ機械・同じデバイスで書き出し、**完全一致**を確かめる。Mac は MPS、箱は CPU で、リランカーのスコアが端数で変わり得るので、機械をまたいで比べない。
- この道具は切り出しの前に、単独のコミットで入れる（政策主張DB の評価の強化として独立に価値がある）。
- **比べ方（2026-10-03 決定）**：(1) 前提＝起動ログの BM25 語彙の n_docs と索引のチャンク数が一致し、比べている間は取込をしない（語彙は索引と別ファイル＝索引だけ新しいと順位が黙って変わる。読み込み時に警告が出る）。(2) 切り出しの前のコードで 2 回回して自己一致を確かめる。(3) 比べるのは file_name の上位 k 件に加えて、問ごとの融合後のチャンク ID の並びとリランカーの生スコア。(4) 前提を満たしたうえで食い違えば、基準は緩めず原因を調べる。M1 のときに見えた 4 問の入れ替わりは、索引を固定すると再現しなかった。

## 3. 最初の範囲

### 3.1 実データ（2026-10-02 のサンプル調査）

**議事の記録は 3 つの型に分かれる。** 取り込みの器を型ごとに分ける必要がある。

| 型 | 例 | 発言の区切り |
|---|---|---|
| **逐語・発言者名つき** | デジタル行財政改革会議の本会議（表題は「議事録等」）・データ利活用制度・システム検討会（表題は「議事要旨」でも中身は逐語）・規制改革推進会議の本会議（表題は「議事概要」）と WG | 「○（氏名）デジタル行財政改革担当大臣」「○（氏名）座長」「○（団体名・部署名）（（氏名）主幹）」 |
| **発言者名つきの要約** | 人工知能戦略専門調査会・人工知能戦略本部 | 「【（氏名）委員】」の見出しの下に「・」の箇条書き／「・（氏名）総務大臣から、「…」といった発言があった。」 |
| **匿名の要約** | AI 戦略会議（構成員は【構成員】）・AI 制度研究会（質疑は □ 問／■ 答）・デジタル行財政改革の戦略チームとアドバイザリーボード（「＜構成員からの御発言＞」） | 発言者を特定できない |

- 表題（議事録・議事要旨・議事概要）と中身の型は一致しない。**型は表題ではなく中身で判定する。**
- 議事録の PDF はすべて Word からの出力で、本文はきれいに取れる。ただし約 40 字ごとに語の途中で改行が入り、ページ番号も単独の行で混じる。出席者の表では氏名が割れる。
- 資料の提出者は資料名の中の「○○大臣提出資料」「○○構成員提出資料」「○○省提出資料」「事務局説明資料」から読める。決まった欄は無い。資料番号の無い資料（デジタル行財政改革会議 第 1 回）、href への改行の混入（同 第 8 回）もある。
- 規制改革推進会議の議事録は、回ごとの議事次第ページからはリンクされておらず、全期の一覧ページにしかない。

**文書数の概算**（サンプル 2〜3 回分からの外挿）

| 会議体 | 概算 |
|---|---|
| デジタル行財政改革会議（本会議 14 回：資料約 140・議事録 14） | 約 160 |
| 同じページにある配下の会議体（データ検討会 16 回ほか） | 約 300〜400 |
| 人工知能戦略本部・専門調査会・推進会議・AI 戦略会議・AI 制度研究会 | 約 130〜150 |
| 規制改革推進会議のデジタル系 WG（デジタル・ＡＩ WG 10 回＋旧デジタル系 35 回） | 約 300 |
| 規制改革推進会議の本会議（令和元年 10 月以降） | 約 300 |
| AI・デジタルに絞った合計 | **約 1,300〜1,600** |
| 規制改革の全 WG まで含めると | 約 3,000 |

AI・デジタル改革推進会議（後継）は、2026-10-02 時点で掲載ページも初回の開催も確認できない。デジタル行財政改革の配下の会議体のうち、共通基盤推進連絡協議会 WT の第 16 回（2026-10-01）はすでに digital.go.jp に載っている＝**移管後の掲載先はデジタル庁**とみてよい。

### 3.2 検討した案

| 案 | 範囲 | 判断 |
|---|---|---|
| (i) | デジタル行財政改革会議の本会議だけ（約 160） | 小さすぎる。型が逐語の 1 つしか試されない |
| (ii) | AI・デジタル関係の会議体を便に分けて（合計 約 1,300〜1,600） | **採用** |
| (iii) | 規制改革の全 WG を含む（約 3,000） | 後で。AI・デジタルの評価問で型が固まってから広げる |
| (iv) | 財政審・法制審など分野を問わず主要な審議会から | 採らない。評価問の主題が散り、型を作る第 1 段に向かない |

**便の分け方と理由**

| 便 | 会議体 | 文書数（概算） | この便で試すもの |
|---|---|---|---|
| **第 1 便** | デジタル行財政改革会議 本会議（14 回）／人工知能戦略本部・専門調査会／AI 戦略会議 | 約 320 | **3 つの型がすべて入る**（逐語・名前つき要約・匿名要約）。大臣・構成員・各省の資料が混在する。決定文書（B26）と同じ議論の過程なので、評価問が立てやすい |
| 第 2 便 | 規制改革推進会議 デジタル・ＡＩ WG／データ利活用制度・システム検討会／AI 制度研究会 | 約 250 | 外部団体のヒアリング資料（経団連・企業・研究者）。□■ の問答の型 |
| 第 3 便 | 規制改革の旧デジタル系 WG と本会議／デジタル行財政改革の配下の残り／AI・デジタル改革推進会議（デジタル庁） | 約 800〜1,000 | 量と、掲載元がデジタル庁へ移ったあとの取得 |
| 見送り | 課題発掘対話・政策改善対話・共通基盤の連絡協議会（実務の報告）・各府省庁 DX 推進連絡会議 | — | 主題が実務の進捗報告で、議論の過程としての価値が低い |

## 4. データの形

### 4.1 メタデータ

共通コア 8 欄（`polyarchy_common.metadata_core`：corpus・org・title・date・date_int・source_url・layer・lang）に、次の拡張を加える。

| 欄 | 中身 | 取り方 |
|---|---|---|
| `org` | 会議体のコード（例 `dgk`・`ai_hq`・`ai_senmon`・`ai_senryaku`・`kisei_ai_wg`） | 取得元ごとに固定 |
| `ministry` | 所管（内閣官房・内閣府・デジタル庁） | 取得元ごとに固定。移管があれば回ごとに |
| `session_no` | 回次（整数）。持ち回りは `mochimawari=true` | 一覧ページ |
| `doc_kind` | `資料`／`参考資料`／`議事録`（逐語）／`議事要旨`（要約） | 資料は一覧のラベル、記録は**中身の型**で判定（表題では判定しない） |
| `material_no` | 「資料１－７」「参考資料４」（無ければ空） | 資料名 |
| `presenter_type` | 資料の提出者区分＝**その会議での役割**：`政務`／`事務局`／`府省・会議体`／`構成員（政府外）`／`外部（ヒアリング）`／`不明`（下の表） | 資料名の型（「…大臣提出資料」「…構成員」「…委員」「…座長資料」「…省提出資料」「…会議提出資料」「事務局…」「法人・団体名＋提出資料」）→ 当たらなければ**表紙の提出者の行**（日付・会議名の行の後）→ それでも無ければ **`不明`** |
| `presenter` | 資料名か表紙に書かれた提出者（個人名・団体名を書かれたとおりに） | 資料名・表紙 |
| `speaker` / `speaker_role` | 議事録の発言者（書かれたとおり）と区分（同じ 6 区分） | 「○」行・【】見出し・開催要領の出席者欄（構成員の欄か、関係大臣等の欄か）。**匿名の要約は `不明`**（推定しない） |
| `page` | ページ（スライド） | 抽出時 |
| `text_quality` | 抽出の質の印（`ok`／`sparse`＝文字が少ない） | §4.3 |

**区分の切り方（2026-10-03 改定）**：人の属性（大臣か・民間か）ではなく、**その会議の中での役割**で分ける。守る線は「政府の側の発言か、政府の外の人の意見か」の 1 本で、役割は記録（資料名・表紙・開催要領の出席者欄）から読める＝推定が入らない。M0 で第 1 便に当てはめ、旧区分（大臣／事務局／府省／民間議員・有識者／外部／不明）では総理・官房長官・副大臣・政務官・座長・自治体の長・会議体の資料が収まらなかったための改定。

| 区分 | 入るもの | 注記（§5） |
|---|---|---|
| `政務` | 総理・大臣・官房長官・国家公安委員会委員長・副大臣・大臣政務官 | なし |
| `事務局` | その会議の事務局（議事要旨・議事録の出席者欄の【事務局】に載る組織）の資料 | なし |
| `府省・会議体` | 府省の資料・別の政府の会議体（とその議長が会議体の代表として出したもの）・会議の下の研究会の資料 | なし |
| `構成員（政府外）` | 民間議員・有識者・座長・構成員である自治体の長 | 付ける |
| `外部（ヒアリング）` | 構成員でない出席者（団体・企業・開催要領で「関係大臣等」の欄に載る自治体の代表 など） | 付ける |
| `不明` | どれにも当たらない（表紙が日付と会議名だけ、など＝会議名は会議の文脈であって提出者ではない） | 付ける（政府の立場と読ませない側に倒す） |

- `policy_tags`（分野 21 分類）は共通の語彙なので付ける（政策主張DB・統計参照DB との突き合わせの軸）。
- 発言者・提出者に**個人名**が入る。公開された会議の公式記録に職名つきで載っている名前をそのまま写すだけで、推定・名寄せ（同一人物を別の会議体と結びつけること）はしない。

### 4.2 チャンクの単位

| 種類 | 単位 | 理由 |
|---|---|---|
| スライド資料 | **1 ページ** | 1 枚で意味が閉じている。意味段落の分割は、図の中で割れた文字列（§4.3）を前後のページとつなげてしまう |
| 逐語の議事録 | **1 発言**（長い発言は上限で切り、同じ発言者を引き継ぐ） | 引用の単位が「誰が何を言ったか」 |
| 名前つきの要約 | 【】見出し 1 つ（＝1 人分の発言の要約） | 同上 |
| 匿名の要約 | 見出し（＜構成員からの御発言＞ など）の下の箇条書きのまとまり | 発言者を割り当てない |
| 文章の資料（Word 由来） | 意味段落（政策主張DB と同じ戦略） | — |

- 議事録は、取り込みの前に行の連結（語の途中の改行・ページ番号の行を除く）を行う。ページをまたぐ発言がある（ページの先頭のページ番号の行を挟んで続く）。
- **本文は取り込みの前に NFKC で正規化する**（M0 の実測：第 1 便の 55 本の PDF に「⼈⼯知能」のような康煕部首の字形が混じる＝正規化しないと BM25 が「人工知能」に当たらない）。返す本文の抜粋も正規化後の文字列にする。
- **チャンク ID は文書・ページ・連番から作る決定的な uuid5** にする（政策主張DB は llama_index の乱数 ID で、再取り込みのたびに変わる＝並びの比較や差し替えに不便だった）。

### 4.3 スライドの文字抽出

サンプル 3 本（第 14 回 資料 1＝大臣の PowerPoint・同 資料 10＝構成員・規制改革 WG 第 6 回 資料 1＝経団連）の実測：

- 1〜3 文字の短い行が **20〜22%**。図の中の文字が「防|災|医|療|・|介|護|DX」のように 1 字ずつ割れる。
- 図そのものが画像で、文字がほとんど取れないページがある（全体相関図のページで 41 字だけ）。写真中心の資料は 5 ページで合計 561 字。
- PyMuPDF の `get_text()`（既定）は PowerPoint のオブジェクト順で、ページ下端の帯が先頭に来ることがある。ただしブロックの単位は保たれる。`get_text(sort=True)` は上から下に並ぶが、**2 段組の左右が 1 行に混ざり、縦書きの字が行末に紛れ込む**。

**判断**
- **既定の `get_text()` を使う**。順序の乱れは 1 ページ＝1 チャンクの中で閉じ、検索（BM25・ベクトル）にはほぼ効かない。`sort=True` の左右の混線は語を壊すので、検索に効く。
- 1〜3 文字の行は、ブロックの中で隣の行と連結する（ブロックをまたいでは連結しない）。
- 文字数が閾値に届かないページは `text_quality=sparse` とし、**捨てずに残す**（資料が存在する事実と出典は返せる）。
- **OCR は第 1 便では入れない**。第 1 便の取り込みで `sparse` のページの割合と、評価問の取りこぼしへの寄与を測ってから決める。

## 5. 公開するツール

- **`search_deliberations`**：ハイブリッド検索。絞り込み＝会議体・期間・`doc_kind`・`presenter_type`／`speaker_role`。`layer` 引数は作らない（公開固定）。

## 6. 評価（問を先に立てる）

既存のアンカー（hit@5・MRR）の型に加えて、このサービスの約束を測るゲートを置く。

| ゲート | 測るもの | 基準の置き場 |
|---|---|---|
| 検索のアンカー | 過程を追う問（第 1 便の会議体で 30〜40 問）の hit@5・MRR | ルート README（取込と同じコミットで新設） |
| **帰属の正しさ** | 提出者区分・発言者の付与。人手でラベルを付けた資料・発言の集合で、**取り違え 0 件**（不明は可・誤りは不可） | 同上 |
| fail-closed | 匿名の要約から発言者が出てこないこと・推定で区分を埋めていないこと | 機械検査（全件） |
| 層 | 公開層以外が返らないこと | 既存の層ゲートと同型 |

**評価問の型（例）**
- 「第 14 回デジタル行財政改革会議で、デジタル行財政改革担当大臣の提出資料は、会議の改組について何と書いているか」（大臣・回次の特定）
- 「人工知能戦略専門調査会で、AI のリスク対応について委員からどんな意見が出たか」（名前つき要約）
- 「AI 戦略会議で構成員から出た○○への懸念は」（匿名の要約＝発言者は `不明` で返ることを含めて確かめる）
- 「取りまとめ 2026 の会計 DX は、会議でいつ・誰の資料で最初に出てきたか」（決定文書との往復。正解は審議会DB 側の回と資料だけで測り、政策主張DB とは混ぜない）
- 「初めて出た回」の型（D）の正解は**回と文書**だけにする。同じ回で複数の人が触れることがある（M0：第 1 便の「バーティカルAI」は初出の回で 5 人）＝発言者は許容解（`acceptable_speakers`）として残し、正解にしない。測りたいのは初めて出た回にたどり着けるかどうか。
- M0 の下書き（2026-10-03）＝`deliberations/eval/draft/`（問 40・資料 40・発言 42〔名前あり 31・匿名 11〕）。確認シートは JSON から `make_sheet.py` で作る（手で直さない）。表紙の全文は git に入れず、提出者の根拠の行だけを残す（§7）。

## 7. 再配布条件

- サイトの規約：内閣官房（コピーライトポリシー 2025-03-31）・内閣府（ホームページ利用規約）とも**公共データ利用規約（第 1.0 版・PDL1.0）**。
- ただし PDL1.0 §1.2 は、第三者が権利を持つものについては「利用者の責任で」許諾を得るよう求めている。サンプルした提出資料（構成員・経団連）にも会議のページにも、著作権・転載の注記は無かった。**構成員・外部団体の提出資料は、PDL1.0 の対象外（第三者の著作物）と扱うのが安全**。

**検討した案**

| 案 | 内容 | 判断 |
|---|---|---|
| a | すべて PDL1.0 として扱う | 採らない（§1.2 の読み方として危うい） |
| b | 第三者の資料は取り込まない | 採らない（外部団体のヒアリング資料こそ過程の中身） |
| c | 第三者の資料は**政策主張DB の経済団体の文書と同じ枠**（所在検索に伴う軽微な抜粋＋出典・原文 URL＝[recommendations/docs/再配布条件.md](../recommendations/docs/再配布条件.md) の 47 条の 5／32 条の整理）で扱い、`license` 欄で PDL1.0 の資料と区別して返す | **採用（2026-10-02 決定）** |

- c は既存の整理の延長だが、**有償で提供する者は事前に専門家のレビューを受ける**、という既存の注記（[残タスク](残タスク.md) C5）がそのまま及ぶ。
- 実装の前に `deliberations/docs/再配布条件.md` を 1 枚作り、取得元ごとの判定を書く。

**取得の作法（2026-10-03 決定）**：既定は curl 相当の UA・1 リクエストごとに 1 秒以上あける・JS チャレンジ／ログイン／レート制限は突破しない（stats と同じ）。**例外＝cas.go.jp（内閣官房）**は curl の UA に 404 を返す（UA の文字列で弾く型＝中小企業白書の PDF と同じ）ため、ブラウザの UA で取得する。robots.txt は cas.go.jp・cao.go.jp とも置かれていない（2026-10-03）。

## 8. 箱の資源

### 8.1 実測と見積もり（2026-10-02・手元の Mac）

- ruri（埋め込み）とリランカーを 1 組読み込んだプロセスのピークのメモリは**約 1.2GB**（torch と llama_index の import だけで 0.26GB、ruri で＋0.5GB、リランカーで＋0.4GB）。Mac は MPS。箱は CPU で fp32 なので、**箱の値は別に測る**。
- 手元の Qdrant（政策主張DB の 3 コレクション＝約 42 万点）は 1.6GB。審議会DB の第 1〜3 便は数万チャンクの見込み（768 次元の dense だけで 1 万点あたり約 30MB）で、Qdrant の増分は小さい。
- 起動時に全チャンクの本文とメタデータを辞書に載せる仕組み（§2.3 (d)）も、チャンク数に比例して小さい。

### 8.2 検討した案

| 案 | 内容 | 判断 |
|---|---|---|
| 別プロセス（1 コーパス＝1 プロセス） | モデルがもう 1 組載る（約 1.2GB〜） | **原則**（[長期開発計画](長期開発計画.md) §3：障害分離・独立デプロイ・ゲートの独立） |
| 政策主張DB のプロセスに同居 | モデルを共有 | 採らない（同上の原則に反する） |
| モデルだけを別サーバにする（埋め込み・リランクの API） | 全サービスでモデル 1 組 | いまは採らない（新しい構成要素が増え、遅延と障害点も増える）。3 つ目の文書検索コーパスでメモリが詰まったら再検討 |

**判断**：箱（t3.xlarge・16GB）には余地がある見込み。ただし稼働中の各ユニットのメモリを運用ダッシュボード（ユニットごとのメモリを表示している）か運用側への依頼で確かめてから、載せるかどうかを決める。**開発・取り込み・ゲートは手元で完結する**ので、この判断は着手を止めない。極小スペック（[残タスク](残タスク.md) C6）の 8GB 案では、2 プロセスのモデル（2.4GB〜）が効いてくる。C6 の実測に審議会DB も含める。
