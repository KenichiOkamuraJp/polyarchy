# 文書管理ルール（プロジェクト共通・他プロジェクトへ持ち出し可）

> **状態：設計（安定リファレンス）。** 起案 2026-09-04（本リポジトリで 2026-08〜09 に定着した運用を 1 枚に抽出）。
> 本文（§0〜§12）は**固有名詞を含まない**＝別プロジェクトの `docs/` にそのまま複写して使う。本リポジトリでの実例は付録 A、書式のテンプレートは付録 B。
> 持つもの＝文書の分類・置き場・更新の規則。持たないもの＝個々の文書の内容・コードの規約。

## 0. 目的（1 行）

**「どれが今の正解か」を探させない。** 定義・数値・タスクはそれぞれ 1 箇所にだけ書き、他の文書はそこへリンクする。
生きている文書と凍結した文書を分類で見分けられるようにし、新しい人（人間・AI セッション）が README の地図から迷わず入口へ着けるようにする。

## 1. 分類（4 種＋git 外 1 種）

| 分類 | 定義 | 更新 | 典型 |
|---|---|---|---|
| **正典** | 生きている文書。**その話題の現在の答えはここだけ** | 事実が変わるたびに更新する。更新先はここ以外にない | README・用語集・残タスク・運用設計・runbook・各サービスの入口 README・契約 |
| **設計** | 安定リファレンス。判断の根拠と構造 | **判断が変わった時だけ**更新。現行の実装名・数値は持たず正典へリンク | 長期計画・環境方針・設計判断書・対外説明文書・ひな型・移行手順 |
| **記録** | 凍結。日付つき。ある時点の事実・所見・監査結果 | **更新しない**。進捗は正典へ書く。読み替え表として参照 | 監査結果・リファクタ所見・調査結果・開発経緯・往復書簡 |
| **規約** | セッション作業規約。新しい開発者・AI が最初に読む | 運用が変わった時に更新 | `CLAUDE.md`（フォルダ単位） |
| **社内ノート**（git 外） | 内部事情・決定理由・交渉スタンス・相手方情報 | 自由 | `社内ノート/`（`.gitignore` と配布 tar の両方で除外） |

原則：
- **どの文書も冒頭で自分の分類を宣言する**（§2）。宣言のない文書は地図に載せない。
- 分類は文書単位。1 つの文書に正典と記録を混ぜない（混ざったら記録部分を §E 対応履歴か別ファイルへ移す＝§5）。
- 「正典」は話題ごとに 1 つ。同じ話題の正典が 2 つあると気づいたら、片方を設計か記録に降格し、もう片方へリンクする。

## 2. 文書の冒頭に書くこと（状態宣言）

1 行目＝タイトル。2 行目以降に引用ブロックで以下を書く（書式は付録 B）。

1. **状態**＝分類と、必要なら括弧で性格（凍結・日付／ドラフト・法的文書ではない／各論＝契約値のみ 等）。
2. **起案日と主な改訂日**（相対日付は使わない。「先週」「次回」は絶対日付に直す）。
3. **持つもの／持たないもの**＝この文書が答える範囲と、答えない範囲の**行き先**（例：合格基準は README「品質の担保」・進捗は残タスク）。
4. 記録なら **「更新しない。進捗は〔正典名〕に書く」** を明記。設計なら **「現行の実装名・数値は〔正典名〕」** を明記。
5. 更新の仕方が定型なら 1 行（例：「バッチが終わるたびに §1 の現状と §3 の状態列を更新する」）。

## 3. 「正典は 1 箇所」（定義・数値・タスク）

| 種類 | 正典 | 他の文書がすること |
|---|---|---|
| **定義**（役割・段階・用語・内部語） | 用語集 1 枚（`docs/用語と役割.md` 相当） | リンクする。写さない。内部語（略号・記号・環境名）は用語集で定義してから使う |
| **数値**（品質基準・現在値・規模） | ルート README の 1 節（「品質の担保」相当） | **写さない**。「基準はルート README」とだけ書く。数値を写した文書は必ず古くなる＝監査で最初に割れる |
| **タスク**（これからやること・経緯） | 残タスク 1 枚（`docs/残タスク.md` 相当） | 進捗をここ以外に書かない。設計・記録の中の「残り」は残タスクの行番号を指す |
| **契約値**（外部と約束する上限・既定値） | 共通契約（§7） | 実装名は docstring、値は契約文書、手順は runbook に分ける |
| **仕様の詳細** | コードの docstring | 文書は「何があるか・どう使うのが契約か」の 1 枚に留め、詳細は docstring が常に優先 |

数値を扱う変更は**同一コミット**で正典を更新する（評価問を足したら基準値の行も同じコミットで直す）。

## 4. README ＝地図

- ルート README に **「ドキュメント（地図）」** 節を置き、**話題 × 分類（正典／設計／記録）の表**にする。行は話題（総論／開発計画・評価／サービス／運用／導入先向け／規約 等）。
- **新しい文書は分類を宣言し、地図に登録するまで「存在しない」**。登録を忘れた文書は次の監査で拾う。
- 各セル＝リンク＋「＝何が書いてあるか」の 1 句。新しいセッションが最初に読むべき記録には **（新しいセッションはまずこれ）** を付ける。
- 地図の凡例＝分類の定義を 1 行で書く（§1 の要約）。
- サブフォルダ（サービス単位）の README は**その入口**であり、全体の数値・基準は写さずルート README へリンクする。
- 地図の重複を作らない（残タスク末尾などに「記録の場所」表を二重に持たない＝1 行ポインタに縮める）。

## 5. 残タスクの運用

- 表の列＝**#／タスク／条件（または前提）／ステータス／手順・根拠**。
- **タスク列は課題の定義のまま保つ**（済んでも書き換えない）。進捗・完了は**ステータス列**に書く。**行は消さない**（経緯が追える）。
- **ステータス列は現状サマリ 1〜2 行まで**。長くなった経緯・実測・地雷は末尾の **§E 対応履歴**（追記のみ・書き換えない・見出しにアンカー `<a id="e-xx">`）へ移し、ステータス列からは「詳細＝§E-xx」で指す。
- 節は待ち（条件付き）／いつでもできる（価値順）／経営判断が要る／長期 のように**着手条件で分ける**。
- 「キック文書」（1 回限りの作業指示）は実行が終わったら**削除**し、残タスクに「削除＝git 履歴で参照可」と 1 行残す。

## 6. 凍結・改名・削除

- **記録は凍結**＝ファイル名に日付（`_YYYY-MM-DD`）を付け、冒頭に「更新しない・進捗は〔正典〕」を書く。サービス配下は `docs/記録/` にまとめてよい。
- 正典・設計が役目を終えたら**記録に降格**して凍結する（消さない）。改名・縮約したときは冒頭に「旧名〔X〕・YYYY-MM-DD に改名」を残す。
- 大きな配置換え・改名をしたら **読み替え表**（旧→新）を記録として 1 枚残し、古い記憶・記録は「この表で読み替える」と書く。
- 凍結文書に古い名前・数値が残っていても**直さない**（凍結の意味が失われる）。読者への注意は正典側に「凍結記録は旧名のまま」と 1 行。
- 削除は git 履歴で参照できるものに限る（キック文書・作業用の一時文書）。

## 7. 共通契約の階層（複数サービス・複数モジュールがある場合）

- **共通部の正典 1 枚**（共通パッケージの README）＋**各論 1 枚／サービス**（`<service>/docs/共通契約.md`）の 2 層。
- 各論は「**親を読まずに済むための 1 枚**」＝そのサービスが**外から受け取るもの・外へ約束するもの**だけ。ここに無いものはそのサービスの自由。
- 各論は**契約値のみ**（上限・既定値・名前・配信形）。手順（runbook）と経緯（記録）を持たない。
- 共通部の詳細仕様は docstring（常に優先）。文書は「何があり・どう使うのが契約か」。
- 各論に共通部を写さない。写していたら共通部へ昇格させて一本化する（重複が出た時点で階層を作る）。

## 8. セッション規約（`CLAUDE.md`・フォルダ単位）

新しい開発者・AI セッションが最初に読む 1 枚。項目は固定：

1. **状態宣言**（規約）。
2. **読む範囲（厳守）**＝読んでよいフォルダ／**読まない**フォルダ。必要なのは契約だけで、それは共通契約の 2 枚に書いてある、と示す。他モジュールの実装を確認したい時はサブエージェントに「契約だけ返せ」と投げ、本文を流入させない。
3. **このモジュールの性格**＝設計上の不変条件を 3〜5 行（何をしない・何を返さない）。
4. **実行**＝コマンド数本（cwd の指定つき）。ゲートの基準は README へリンク。
5. **利用セッションの振る舞い**（ドッグフーディング時）＝勝手に実装しない・`git commit` しない・気づきは捕捉ログや残タスクへ。
6. **運用地雷**＝★付きで 3〜6 行。**複数の規約に同じ地雷を転記してよい**（規約は正典の例外＝地雷は重複を許す）。
7. AI の記憶（memory）はフォルダごとに別系統。共有すべき地雷は規約へ転記して残す。

## 9. git に書かないもの（社内ノートへ）

- git に含めないのは **3 種だけ**＝**相手方（導入先・取引先）の情報／個人情報と実利用ログ／秘密（鍵・トークン・state）**。これは「開示範囲」の問題ではなく**最初から含めない**。
- 加えて、公開・共有リポジトリには **内部事情**を書かない＝所属組織の事情・交渉スタンス・決定の理由・対価や契約の条件・個人の動機・立場の言語化・構想段階のビジネスモデル。**git には構造（原則・条項・手順）だけ**を書く。
- 置き場＝リポジトリ内の `社内ノート/`（`.gitignore` でディレクトリごと除外＋**配布 tar の除外リストにも同じ行を置く**＝gitignore は tar に効かない）。新規ノートは自動で保護される。
- 対外文書は**共有版と作業版を分ける**。作業版（内部分析・決定理由）は社内ノート、共有版（条項・手順のみ）は `docs/`。共有版から作業版へリンクしない（相手に見える）。
- 社内ノートも冒頭に状態宣言を書く（**状態：社内ノート（git 外）**）＝どの文書が git 外かを本文だけで判別できるようにする。
- 相手方へ渡す資料は社内ノートから抜き書きせず、**方針だけを別に 1 枚書き下ろす**。

## 10. 対外文書の書き方（導入先・監査人・法務に読まれる文書）

- **内部語は初出で定義する**か用語集へリンクする。内部 ID（タスク番号・段番号・環境名）は対外文書から除く。
- **役割名は法的主体（契約の当事者）と作業上の役割を分ける**。同じ人が兼ねることは表で示す。
- **到達目標を現状として書かない**（「移譲済」と書けるのは移譲した後）。現在の担い手と移行条件を分けて書く。
- **約束を減らす**＝「改良され続ける」「〜し続ける」より「壊れない仕組み」「止まっても残る」「出て行ける」を書く。主語を人ではなく構造にする。
- 数値・定義は §3 のまま（対外文書でも写さずリンク）。ただしリンク先が読者に見えない場合は、その時点の値を「YYYY-MM-DD 時点」と日付つきで書く。
- 法的文書でないひな型・ドラフトは状態宣言に「法的文書ではない」と明記する。

## 11. 文書監査（体系と実装の一致）

- **タイミング**＝相手方へ連絡する前・大きな改訂の後・移管の前。
- **方法**＝観点別に走査（①体系＝分類・地図・リンク ②運用設計×コード ③対外文書・移行手順×コード）。重要度 高の指摘は**実環境・設定・コードで裏取り**してから記録する。AI サブエージェントを観点ごとに並列で使うと速い。
- **出力**＝記録 1 枚（凍結・日付つき）。優先度 3 段＝**1 実害あり（コード・設定）／2 相手に見せる前に直す（文書）／3 体裁**。一致を確認した項目も「安心材料」として列挙する。
- **対応**＝残タスクに 1 行起票し、束ごとにコミット。監査記録自体は更新しない。
- **機械検査**＝相対リンク切れゼロ・状態宣言の有無・数値の二重管理（同じ数値が複数文書にある）・凍結文書への差分。

## 12. 新プロジェクトへの導入手順

1. `docs/文書管理ルール.md` として本書の §0〜§12（付録は不要）を複写する。
2. ルート README に「ドキュメント（地図）」節（付録 B-2 の表）を作り、凡例に 4 分類の 1 行定義を書く。
3. 正典 3 枚を最初に作る＝**用語集**（役割・段階・用語）／**残タスク**（付録 B-3 の表＋§E）／**README の数値 1 節**。既存文書があれば分類を宣言して地図に載せる。
4. `.gitignore` に `社内ノート/` と秘密（`*.env`・`*.tfstate`・鍵）を置き、配布物を作るスクリプトがあれば同じ除外を置く。
5. フォルダ単位の `CLAUDE.md` を §8 の項目で 1 枚。
6. 以後、文書を足すたびに「状態宣言 → 地図に登録」。数値を変えたら同一コミットで正典を更新。相手方へ出す前に §11 の監査。

`CLAUDE.md` に貼る短縮版（5 行）：

```
- 文書は 4 分類（正典／設計／記録／規約）＋社内ノート（git 外）。冒頭の「状態：」で宣言し、ルート README の地図に登録する。
- 定義は用語集・数値はルート README「品質の担保」・タスクは残タスク＝正典は 1 箇所。他の文書は写さずリンクする。
- 記録（日付つき）は更新しない。進捗は残タスクのステータス列（1〜2 行）、経緯は §E 対応履歴（追記のみ）。
- 相手方情報・個人情報／実利用ログ・秘密・内部事情は git に書かない＝社内ノート/ へ。
- 対外文書は内部語を定義してから使い、到達目標を現状として書かない。
```

### B-3 残タスク

