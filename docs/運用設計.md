| **② 更新** | 既存データの更新（提言の新着取込・統計の改定反映）＝**更新サイクル** | 運用者（人為・1 コマンド） | `update.sh`／`stats.ops.refresh`・`qe_update` → `release.sh` → 箱の自動適用 | §2 |

| **⑥ 再構築** | 新モジュール（新コーパス等）・基盤変更 | PdM | 設計文書 → レビュー → 建て直し | §5 |

（監査人＝導入団体のシステム担当は全層を ReadOnly で独立検証＝監査ガイド。コード・文書・ゲートは公開リポジトリと CI で誰でも再現できる。）

**役割と移譲の段階（2026-09-04）**＝導入団体側の役割は **PdM**（問を決める・評価問の採否・main のマージ権＝配布の承認）と**開発者**（PR を書き軽いゲートを緑にする）の 2 段（定義＝[用語と役割.md](用語と役割.md) §1b）。どちらも Claude Code に適切に指示を出せる人であって、プログラミング能力は要件でない。
移譲は層の順に進む：**層② 更新 → ③ 定型拡充**を運用者・開発者へ → **卒業判定**で ④ 新種の収録・⑤ 燃料サイクルの採否・⑥ 再構築の**承認**も導入団体の PdM へ（提案は最初から誰でもできる）。
**卒業判定**＝自分で計画と評価問を書き（TDD＝問が先）、新種の収録の PR をゲート全通過で通せること。**到達した人は誰でも PdM**（承認者）になる＝PdM は固定の 1 席ではなく、卒業した人の数だけ増える（自分の提案は自分で承認しない規則は維持）。
計測＝担当者の PR 数・緑（全 PASS）になるまでの時間・評価問を先に足した PR の割合（CI 化後は PR の履歴がそのまま記録になる）。

**境界原理（運用者・開発者と PdM）**＝**品質ゲートが検出できる失敗は運用者・開発者、意味の判断は PdM**。取得ミス・件数ズレ・検索劣化は
ゲートが自動検出する。意味の取り違え（年度/暦年・名目/実質・混ぜてはいけない組合せ）はゲートで捕まらない（評価問を書く人が
同じ勘違いをすれば通る）＝PdM の判断が要る。

**安全網＝fail-closed ＋ fail-back**：誤操作の最悪結果は「リリースが起きない」（release.sh がゲート全 PASS 時のみ配布・箱は検証済み
マニフェストにのみ反応）。適用に失敗しても「旧版で動き続ける」（自動切り戻し・§2.4）。壊れたものが配信されることは構造的に無い。

**運用者ロールを非開発者が担うための条件**。更新サイクルの初回実運用で異常系 2 件（catalog タグ消失・Qdrant WAL 混在）を
踏み、いずれも恒久修正まで完了したが、異常時の診断と復旧には開発者の力が要ることが実証された。非開発者が担うのは次の 3 つが揃ってから：
(1) 更新サイクルが**連続して無事故で周回**した実績（目安 5 回以上）／(2) 適用失敗時の**自動切り戻し**＝**済（2026-09-03・staging で演習済）**／
(3) 異常時に **RUNBOOK の手順だけで復旧できた**実績（開発者の即興判断なしで閉じた事例）。
**CI 化（§2.5）で (1)(3) は仕組みで満たされる**＝ゲートも release も運用者の Mac で走らなくなり、運用者の仕事が「PR をマージ」に縮む。

既にある土台：systemd `Restart=always`・Tunnel 多重接続・WAF（秘密パス／レート制限。IP 許可は 2026-08-28 廃止）・CloudWatch EC2 標準メトリクス・
journald・捕捉ログ（30 日）・S3 versioning・個人認証（案 B・2026-09-02〜）。

## 1. 監視（層①）

### 1.1 生き死に（可用性）
- **`/healthz`**（`polyarchy_common.mcp_http`・GET・認証不要・WAF 除外済）：stats＝レジストリ読込＋代表 1 系列の lookup、recommendations＝Qdrant collection count。応答 `{ok, service, checks}`。
- **箱内監視**：`polyarchy-health.timer`（毎分）→ `curl localhost:8765|8766/healthz` → CloudWatch（namespace `polyarchy`・metric `health`・dimension service）＋ルートディスク使用率。
- **アラーム**：health 3 分連続 0/missing（missing も異常＝箱ごと死んだ場合を拾う）・EC2 `StatusCheckFailed` → SNS → メール（`ALERT_EMAIL`）。
- **トンネル断**：Cloudflare ダッシュボードの Tunnel Health 通知（無料）を ON。外形監視（UptimeRobot 等）は任意＝公開 URL の `/healthz` は 200 で答える。
- **リリース中は health が 1 往復 ALARM→OK する（想定内）**＝停止→bootstrap→再起動が 3 分を超えるため（RUNBOOK §5）。

### 1.2 異常検知
- **アクセスログ**：`polyarchy_common.httplog`（時刻・メソッド・パス・status・所要 ms・`user_hash`・`cf-ray`。本文・検索語は載せない）→ journald → rsyslog → CloudWatch Logs `polyarchy/{mcp,stats,dataapply}`（**保持 30 日**＝プライバシーポリシーと一致）。
- **アラーム一覧**（すべて SNS → メール。閾値は控えめ＝誤報でメールが無視されるのが最悪）：

| アラーム | 条件 | 意味 |
|---|---|---|
| health-mcp／health-stats | health<1 が 3 分連続（missing 含む） | サービス停止・箱死亡 |
| ec2-status | StatusCheckFailed 2 分連続 | インスタンス障害 |
| disk | ディスク使用率 > 80% | ログ・退避領域の肥大 |
| 5xx-mcp／5xx-stats | 5 分で 5 件超 | アプリ異常 |
| 401-mcp／401-stats | 5 分で 30 件超 | 認証失敗の急増＝攻撃 or 設定壊れ（aud 不一致） |
| dataapply-rollback | 自動適用が切り戻された（dataapply=0） | リリース不採用（旧版で稼働中・§2.4） |

### 1.3 運用ダッシュボード（2026-09-03・実装済）
目的＝**箱のシェルへ入らずに状態が見える**（シェル監査を最終手段に限定＝監査ガイド §3）。`polyarchy_common.ops_dashboard` が静的 HTML 1 枚を
毎時生成し S3 `ops/dashboard/index.html` へ保存（`polyarchy-dashboard.timer`）。4 区画＝**①稼働**（ユニット状態・healthz・ディスク）
**②バージョン・規模**（コード版＝upload 時の git describe・データ版＝released/applied・出荷時のゲート数値・smoke・APPLIED/ROLLED_BACK）
**③データ鮮度**（団体別 last_ingested・提言の新着・stats 取得元の変化・QE edition）**④利用**（直近 4 週の件数のみ）。
検索語・文書名・個人情報は載せない。閲覧＝ReadOnly アカウントで S3 コンソールから。

### 1.4 更新チェック（2026-09-03・実装済）
`polyarchy-updatecheck.timer`（毎日 06:10 JST）が ① `stats.ops.freshness --json`（取得元の Last-Modified/ETag・e-Stat の最新期・国際機関の最新期＝
`ESTAT_APP_ID` は SSM から）② `recommendations.ingest.check_new`（5 団体の目次走査＝catalog 未収録の新着数・ダウンロードなし）を実行し、
③ダッシュボード③へ反映。**チェックのみ＝取込は実行しない**（取込は §2 の品質ゲート経路が唯一）。自動適用の直後にも 1 回走る（「新着 N 件」が
取込後に残らない）。手動キック＝SSM ドキュメント `polyarchy-<env>-check-updates`（AWS コンソールの Run Command＝IAM で実行者を限定・CloudTrail に記録）。

## 2. 更新サイクル（層②・③）

### 2.1 経路の全体（人手の箱操作ゼロ）
```
手元（運用者）                                  S3                    箱（無人）
update.sh / refresh / qe_update ──→ release.sh ──→ data/ code/ ──→ dataapply.timer（15 分毎）
   取込・追い判定・増分取込         ゲート 9 本      release/data.json     退避→停止→コード反映→同期→再起動→smoke
                                   全 PASS のみ      （マニフェスト）       PASS＝APPLIED／FAIL＝旧版へ自動切り戻し
```
- 公開ページで「値は月次で更新」と約束済み＝更新は運用の必須項目。何を更新すべきかは §1.4 の毎日のチェックが教える。
- 手順の正典＝RUNBOOK §5。すべての工程が記録経路（CloudTrail データイベント・journal→CW Logs `polyarchy/dataapply`）を通る。

### 2.2 stats（統計の改定反映）
- **存否確認**＝`stats.ops.freshness`（§1.4 で毎日・手元でも随時）。終了コード 0=変化なし／1=更新あり／2=取得失敗。
- **差分更新**＝`stats.ops.refresh --dataset <コード名>`（各 ingest は冪等＝`--all` 再実行が差分更新を兼ねる）：freshness で対象を特定 →
  該当 ingest 再実行 → ゲート（test_core・mcp_smoke・exact_match・find_quality）→ seed_registry で `last_period` 反映 → `git diff` を人が確認してコミット
  （自動コミットしない）→ `release.sh`。QE は `stats.ops.qe_update`（edition 運用）。
- **人手が要る分岐（仕様）**：改定で評価正例の値が変わると exact_match が落ちる＝黙って上書きしない関門。評価セット側の期待値を新 vintage で更新するか、
  改定を所見に記録して判断する。完全自動化（vintage の自動判定）は将来の課題。

### 2.3 recommendations（提言の新着取込）
- **存否確認**＝`recommendations.ingest.check_new`（§1.4 で毎日）。
- **差分取込**＝`deploy/scripts/update.sh <env>`（新着のある団体だけ collect → 分野タグ・文書性格の追い判定 policy_tagger → `qdrant_ingest` 増分 → `release.sh`）＝1 コマンド。
  `catalog.csv` の差分はレビューしてコミット。
- **評価アンカー**：コーパスが増えると hit@5 の分母環境が変わり得る＝`release.sh` のアンカー非劣化ゲート（`REQUIRE_HIT5`／`REQUIRE_MRR`）が門番。
  初回実運用 2026-09-03（10 件取込・数値不変）。

### 2.4 リリースと自動適用（2026-09-03・実装済）
- **配布**＝`deploy/scripts/release.sh <env>`：ゲート 9 本（recommendations 4＋stats 4＋共通 1）全 PASS のときだけ upload → `release/data.json`
  （出荷時のゲート数値・code_version・released_at）。1 本でも FAIL なら S3 に何も置かれない。
- **箱の自動適用**＝`polyarchy-dataapply.timer`（15 分毎）がマニフェスト変化を検知：退避（rsync 2 段）→ 停止 → **code tar 再展開**（コード変更も同じ経路・
  手動の tar 再展開は廃止）→ qdrant ミラー同期 → bootstrap（データ差分 sync・依存再解決）→ 再起動 → smoke → ダッシュボード。
- **自動切り戻し（fail-back）**：smoke FAIL・qdrant 起動不能・反映途中の失敗のいずれも、退避した旧データ＋前回 tar へ自動復帰 → smoke 再実行 →
  マーク `ROLLED_BACK` → メトリクス dataapply=0 → アラーム。不採用マニフェストは再試行しない（再適用ループを防ぐ）。演習手順（訓練フラグ）＝RUNBOOK §5「切り戻し後」。
  初回演習 2026-09-03＝FAIL 判定から復帰まで約 2.5 分。

### 2.5 CI 化（計画・2026-09-04）＝ゲートを PR に紐づける・CD は既存のまま
現状＝CD は完成している（ゲート 9 本＝テスト／S3 マニフェスト＝成果物置き場／`dataapply.timer`＝pull 型の無人適用／自動切り戻し）が、
**ゲートが運用者の Mac で走り PR に紐づかない**＝他人が再現できない。公開リポジトリなら GitHub Actions は無料＝ゲートを CI に移す。

| 段階 | 内容 | 状態 |
|---|---|---|
| 1 | **軽いゲート**（`test_core`・`test_common`・mcp_smoke×2＝データ不要・鍵不要）を **PR ごと**に走らせる＝「PR に赤/緑」 | 未 |
| 2 | **重いゲート**（retrieval・filter・multistage・exact_match・find_quality）を **main マージ時＋夜間**に走らせる。データは S3 の配布済みデータを CI が読む（GitHub OIDC→AWS ロール・読取のみ）・Qdrant は CI 内の Docker。評価問を触った PR は重い側も走らせる | 未（技術的な山＝データの持ち込み方。縮小スナップショットで非劣化を見て、main では全量で正典の数値を測る 2 段が現実的） |
| 3 | **release を CI へ**＝main マージ → CI がゲート → 全 PASS なら CI が upload＋マニフェスト（S3 書込権限は CI ロールに限定）。**運用者の仕事＝PR をマージ**（Mac も鍵も不要） | 未 |
| 4 | **PR テンプレート**＝「評価問を先に足したか」のチェック＝型の教材 | 未 |

変えないもの＝箱の自動適用・切り戻し（CD 側）・「人手の箱操作ゼロ」「管理 Web アプリは作らない」・ゲートの中身と基準値（CI 化は実行場所の移動であって評価の変更ではない）。
昇格（staging→prod）は同じ成果物で行う（[開発環境方針.md](開発環境方針.md) §7 の昇格パイプラインを CI に載せる）。

### 2.6 サプライチェーンと配布物の完全性（設計・2026-09-04）
構造上消えている事故（機密の漏えい・書込の悪用・LLM の乗っ取り・ポートからの侵入＝ルート README「設計上の性質」）の外側に残る壊れ方は
**供給元と資格情報**＝①汚染された依存・モデル・イメージが箱に入る ②箱のロールで配布物（S3 `data/`・`code/`）を書き換えられる ③捕捉ログの流出 ④可用性。
対策は「入りにくく・入られても被害が小さく・すぐ作り直せる」の 3 段で、最後の段（冪等な bootstrap＋データは S3＋秘密は SSM でローテーション可＝箱を捨てて数分で再構築）は既にある。

| 段 | 対策 | 状態 |
|---|---|---|
| 入りにくく | 依存のロック＋sha256（`--require-hashes`・更新は PR＝ゲート経由）／モデルの重みを配布物に含め sha256 固定・箱は HF Hub に接続しない／Qdrant バイナリの sha256 検証 | **依存ロック＝済 2026-09-04**（`deploy/requirements/lock-*.txt`・bootstrap ③ `--require-hashes`・RUNBOOK §7）・Qdrant 済・モデルの重みは未（B17 (3)） |
| 被害を小さく | 箱のロール最小化（`data/`・`code/`・`release/` は読取のみ・書込は `ops/`・`query_log/` だけ）／マニフェストの sha256 を apply が検証／外向き通信の許可制（Cloudflare・S3・SSM） | **ロール最小化＝済 2026-09-04**（Get＝data/・code/・release/／Put＝ops/・query_log/・Delete なし・staging apply 済）・マニフェスト検証と外向き許可制は未（B17 (4)(5)） |
| すぐ作り直す | 冪等 bootstrap・S3 versioning・CloudTrail データイベント・SSM ローテーション | 済 |
| CI 側 | アクションの SHA 固定・サードパーティ不使用・release 書込は CI ロールのみ | CI 化（§2.5）と同時（B17 (6)） |

残る受容リスク＝正規の依存の脆弱性。到達経路は認証付きトンネルのみで狭い。収録元サイトの改ざんで注入文が PDF に混ざる可能性は、サーバでなく利用者側の問題＝出典 URL を常に返すことで原典に当たれるようにする。

## 3. 新種の収録（層④）
- **分業はしない**。作りたい人（誰でも）が、計画 1 枚（弾プロセス＝[stats/docs/データ拡充計画.md](../stats/docs/データ拡充計画.md)）と
  **評価問**（TDD＝問が先）と実装を **1 つの PR** にまとめて提案し、**PdM が承認**する。実装の手は Claude Code なので、提案者に要るのは
  「何を収録し、どの値が正しいか」を問として書けることだけ。
- 役割の区別は**提案者と承認者**の 2 つだけ（自分の提案は自分で承認しない＝ブランチ保護）。ゲート全通過が承認の前提。
- ここが「意味の判断」の本体＝年度／暦年・名目／実質・混ぜてはいけない組合せを問として固定する。卒業判定（§0）は、この層の提案を自分で書いて通し、他人の提案を承認できること。

## 4. 燃料サイクル（層⑤）

### 4.1 捕捉ログ（燃料）
両サービスの MCP がツール呼び出しを追記 JSONL に残す（ツール名・引数・件数・時刻・`user_hash`。会話本文は無い）。箱の `data/query_log/`・
`data/stats/query_log/` が原本、fuelsync（毎時）が S3 へ保護コピー。**30 日で削除**（箱の logprune 毎日＋S3 ライフサイクル・両方で担保・
プライバシーポリシーの約束）。手元の `usage_report --s3-bucket` が作るミラー `s3_mirror/` は箱では作らず・prune が消す・fuelsync は戻さない（2026-09-03）。

### 4.2 週次利用レポート（数字のみ・恒久蓄積）
方針＝**管理 Web アプリは作らない**（常設アプリ＝認証・攻撃面・保守の固定費）。`polyarchy_common.usage_report` が捕捉ログから
週次 1 行の集計（`ops/usage/weekly.jsonl`・git 外）と静的 HTML を生成し、箱の `polyarchy-usagereport.timer`（月曜 09:20 JST）が S3 `ops/report/` へ保存。
内容＝サービス別・source 別の件数・フィルタ利用率・0 件率／低ヒット率・found=false 件数・利用者数。**検索語は集計にも HTML にも載せない**＝
恒久保存できるのは個人も検索語も含まない数字だけ（30 日制約の外で履歴として蓄積）。閲覧＝S3 コンソール（監査ガイド §4）。

### 4.3 トリアージ（草稿生成＝運用者・採否＝PdM）
- 週次に `bash deploy/scripts/triage.sh <env>`＝S3 の燃料＋手元の捕捉分 → 両サービスの草稿を `ops/triage/<日付>/` へ（読み取りのみ・評価セットには書かない）。
  stats＝`stats.ops.quality_candidates`（find_quality の問の草稿・zero_or_alias／flood・直後の lookup を target 候補に）・
  recommendations＝`recommendations.ops.quality_candidates`（zero／low／frequent・各行に scaffold コマンド）。
- 採否＝PdM：stats は `quality_candidates --accept <草稿> --ids <id,id>`（追記→ゲート）、recommendations は `phase12_pipeline scaffold → careful 編集 → append`
  （evalset_gate → ユーザー由来へバイト不変追記）。検索型を昇華したらアンカー記載を同一コミットで更新（ルート README「品質の担保」）。
- 30 日で燃料は消える＝**トリアージは 30 日以内に回す**。昇華した資産（識別情報なし）は git 内で恒久＝公開リポジトリの一部として誰でも使える。導入団体の還元への協力は任意。

### 4.4 利用者識別と集計の粒度
個人認証（案 B・2026-09-02〜）で捕捉ログに `user_hash`（メール由来・平文非保存）が 3 経路とも付く＝利用者数・組織別の集計が可能。
規約＝**組織単位の集計のみ恒久保存・個人単位は生ログ同様 30 日**。会社ごとの集計は作り込まず、必要になったら `user_hash` の材料を
JWT クレーム（組織）に切り替えるだけ。プライバシーポリシーは認証と user_hash を明記済（2026-09-02）。

### 4.5 燃料の外側＝任意のログ開示
捕捉ログには「モデルがどう解釈したか」は無い（§評価設計 6-2）。詰まった会話の共有リンク／エクスポートを利用者から任意で受ける経路＝
[実利用ログの提供_同意書ひな型と共有経路.md](実利用ログの提供_同意書ひな型と共有経路.md)（匿名化して転記・原本は削除・学習不使用）。
