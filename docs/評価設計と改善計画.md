## 2. 評価は既に改善している（＝この3つを型として維持する）

「評価方法そのものを改善できるか」への答えは、**既にしている**。実例が3つある。この3つは今後も型として意識的に維持する。

**型①：実使用を評価ケースに変える**
`eval_set_userderived.json` は実利用で得た論点を一般化して評価ケース化したもの。合成問ではなく実分布から来ている。

**型②：踏んだ欠陥を恒久ケースとして焼く**
[stats/eval/mcp_smoke.py](../stats/eval/mcp_smoke.py) の `[3e]` `[3h]` `[3i]` `[3j]` は、第7弾のドッグフーディングで見つけた欠陥（複数語 AND・0 件時の診断・絞り込み由来の 0 件）をそのまま恒久ケースにしたもの。ソース中に弾番号と日付を注記して由来を残す（`# 第 7 弾 段 A（2026-08-22）：…`）。**この注記の書式を今後も守る**——由来が消えるとケースの意味が読めなくなる。

**型③：データ規模が変わったら評価の種類を変える**
`find_golden.jsonl` は `fixed_at` と `must_keep` を持つ。系列が 8,681 本に増えると素朴な golden set は壊れるため、「基線の主要系列が top20 から押し出されないこと」を見る形に**評価の設計自体を作り替えた**。プロジェクトの段階に応じて評価を入れ替える、の実例。

## 3. 構造的に残っている穴

**① 評価は事故の後にしか増えない**
`[3h]` `[3i]` は欠陥を踏んだから存在する。踏む前に書く手段がない。よって評価セットは「過去に壊れた場所の地図」であって「壊れうる場所の地図」ではない。

**② stats に「良くなった」の軸がない → 一部解消（2026-08-29）**
発見層は `find_quality`（到達率）で連続量になった。残る穴＝**参照層の側**（値の正確さは合否のみ）と、
方針 A の「発見率＠20」のような**実資料由来の分布**での測定（find_quality の問は開発者起点が中心）。

**③ 評価そのものを評価していない**
「いまのゲートは、第7弾の欠陥3件を事前に捕まえられたか」——構造上ノー。ゲートの穴を測る手段がない。

## 4. 改善方針

### 方針 A：役所発表資料の検算（要件源と評価セットを同時に出す）— **採用・着手保留**

役所の発表資料（白書・月例経済報告など）に載る数字を stats で引き直し、結果を4分類する。穴 ① への回答。

| 結果 | 意味 | 産物 |
|---|---|---|
| ○ 一致 | 参照できた | 正例が1本増える（実使用由来・出典付き） |
| × 系列が無い | 網羅性の穴 | 拡充候補。優先度が「役所が実際に使った」で自動的に付く |
| × 系列はあるが上位に出ない | 発見層の穴＝埋もれ | ランキング・語彙の改善対象 |
| × 値が違う | **最重要** | 定義のズレ（年度／暦年・名目／実質・季調・改定）→ `analysis_notes` に焼き込む |

4番目が最も価値が高い。値が違うとは、DB を素直に読んだ利用者が公表値と違う数字にたどり着くということで、本サービスが防ぐべき事故そのもの。対処は既存の手口（`coverage_proxy`・`activity_scope` と同じ＝注記をデータ側に構造化する）で足りる。

**副産物＝穴 ② への回答。** ○ のケースについて「lookup の前に `find_statistics` の上位20件に入っていたか」を記録すると **発見率＠20** が得られる。これが stats に唯一なかった連続量。網羅性を上げると発見率は下がる方向に効くため、**両方を同時に見ないと片方の改善が他方を壊すのが見えない**。

**罠が2つ。設計前に必ず分けること。**
1. **加工値。** 発表資料の数字の多くは前年比・寄与度・季調値・実質化後で、stats は意図的にこれらを計算しない（換算・丸め・季調・接続なし＝設計）。加工値を「穴」に数えるとリストが埋まって本当の欠落が見えなくなる。**原数値か加工値かを最初に分け、加工値は対象外と明記する。** なお「この公表値は原数値からこう作られる」という説明だけ返す道はあり、それは `status=guide` と同じ考え方。
2. **改定（ヴィンテージ）。** 発表資料はその時点の値、stats は最新値。ズレて当然であり、バグに数えると誤検出だらけになる。**資料の公表日を記録し、ズレたらまず改定を疑う。**

**進め方＝パイプラインを作らない。** まず資料1本・数字20〜30個を手で4分類し、罠の比率と穴の質を見てから設計する。想定と違えば設計を変える。初回は原典突き合わせが効く中小企業白書あたりが向く。

### 方針 B：変異テスト（ゲートの穴を測る）— **見送り（2026-08-22 判断）**

穴 ③ への回答。診断フィールドを空にする・フィルタを1つ外すなど意図的に壊し、ゲートが鳴るかを見る。数分で組める。今回は優先度が低いと判断して見送ったが、**ゲートが増えて信頼しすぎたと感じたときに再訪する**。

### 方針 C：評価の燃料＝実使用の確保 — **最優先・ただし技術課題ではない**

評価/エラー分析のループは既に組んである。欠けているのは**燃料**＝実トラフィックの分布。現状の燃料は試行での実ユースケース 1 件と開発者自身のドッグフーディングのみ。第7弾の欠陥3件は優れた発見だが、それは「開発者が詰まる場所」であって「利用者が詰まる場所」とは限らない。n=1 の使用から出るエラーは n=100 のそれと種類が違う。

**投資対効果が最も高いのは新技術の導入ではなく、使われる状況を作ること。** 開発者自身のドッグフーディングだけでは評価の燃料が足りない。燃料確保は別建てで扱う（→ [docs/残タスク.md](残タスク.md)）。

**進捗（2026-08-29／09-02）**：燃料を受ける側の回路は完成した——①`stats.ops.quality_candidates`（捕捉ログ→
評価問の草稿・自動追記はしない＝2026-08-29）②**認証の全経路化で計測の盲点が閉鎖**（2026-09-02＝authless 時代は
ChatGPT 経由がログに user_hash なしで混ざり利用計測から漏れた。案 B で3クライアントとも利用者キー付きで捕捉）。
残るは燃料そのもの＝**導入団体展開（残タスク A6 段3）が最初の供給源**になる見込み。

## 5. 埋めないと決めたもの

- **モデル側の改良（ファインチューニング・蒸留）。** 本プロジェクトは「モデルを賢くする」のではなく「モデルに正しい一次資料を渡す」もの＝評価の対象は検索と参照であって、生成モデルではない。
- **リランカーの再選定・大型化。** 日本語リランカー（小型）は本番構成に入っている（ルート README）。候補の比較は `recommendations/archive/rerank_eval.py`・`rerank_bench.py` に記録があり、大型化は [残タスク B21](残タスク.md#e-b21) で「現行維持」と判断済み。再訪するのは実利用の失敗集積がリランカー起因を示したとき。

## 6. 評価まわりの所見（2026-08-22）

評価まわりの判断に効くので併記する。順位は投資対効果順。

1. **実使用（＝評価の燃料）** — §4 方針 C。最大の欠落。手法ではなく入力の欠落なので、評価の作り込みでは埋まらない。
2. **モデル側の読み違えの観測** — 「データは正しいのに読み違えられる」事象はサーバから見えない（捕捉ログは引数と件数のみ）。任意のログ開示（[実利用ログの提供](実利用ログの提供_同意書ひな型と共有経路.md)＝方針 C の経路）で観測可能になり、問いの集合が得られれば複数回・複数モデルでのばらつき測定も開発者側で再現できる。対処のレバーはモデル設定（利用者側の Claude/ChatGPT にあり運営側には無い）ではなく、ツール説明・応答の注記・データ側＝第 9 弾の SERVER_INSTRUCTIONS 対策が先例（2026-09-03 改訂）。
3. **コストとレイテンシの規律** — 体系的には未計測（個別の実測は残タスク B21・C6）。利用者が増える段階で必須になる。

**評価の外にあるが削らない投資**：再配布条件の全件確認、`status=guide` の設計、取得側の作法、定義のズレを注記として構造化すること。最も時間を食い、最も模倣しにくい部分がここ。
