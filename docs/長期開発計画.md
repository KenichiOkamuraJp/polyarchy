## 1. ビジョン

Polyarchy を、経済団体の提言検索から出発して**政策言説の横断検索インフラ**へ育てる。対象は段階的に広げる：

経済団体の公表提言（現行）→ 政府審議会 → 国会議事録 → 地方議会議事録 →（将来）政党の政策文書・外国政府

価値の核は「**誰が・いつ・何を・なぜ主張し、どこで・どう検討され、事実はどうだったか**」を出典つきで横断できること。単独のキーワード検索は各機関の既存サービスで足りる。Polyarchy の存在理由は**比較と突き合わせ**——主張（提言）・審議過程（議事録）・事実（統計）の三角形を突き合わせられることにある。

**商品定義**：AIエージェント時代の「信頼できるコンテキストの発行者」。原資料が公開情報であることは価値を損なわない（判例DBや記事DBと同じく、整備・検索可能性・信頼そのものが商品）。「信頼できる」の成分は5つ——①出所が確か（全文書に出典URL・取得日・発行体）②網羅の機械的検証 ③鮮度の継続維持 ④**検索精度が測定されている**（評価セットと回帰ゲート、実利用の質問による継続更新）⑤運用の約束を守る仕組み（公開層固定・フェイルクローズ・ログ保持期限の機械的担保）。継続性そのものが商品仕様であるため、収集・取り込み・検証の自動化は費用削減ではなく商品価値の直接強化にあたる。

## 2. 設計原理 — 何を基準に分割するか

拡張のたびに迷わないよう、コーパス（DB）の切り方を4つの軸で固定する。

| 軸 | 決めるもの | 判定方法 |
|---|---|---|
| **単声か多声か** | DBの境界 | 機関の結論として引用できる文書（提言・意見・答申・建議・方針＝**主張文書**）か、複数の発言者の記録で個人までしか引用できない文書（議事録＝**過程文書**）か |
| **比較可能性** | 同一DB内に同居するか | リトマス試験＝「利用者が『AとBの主張の差は？』と**1つの質問**で聞きそうか」。聞きそうなら同居 |
| **信頼境界** | 扱う範囲 | 公開資料の収集物のみを扱う。特定組織から預かった非公開データは**境界の外＝本計画では作らない**（2026-09-04）。必要な組織は自組織帰属の別リポジトリで、本ソフトウェアを依存として使う。層（公開固定・フェイルクローズ）の不変条件は共通契約に残す |
| **参照の厳密性** | サービスの内部アーキテクチャ | 近似でよいもの（文書）→ ベクトル検索。厳密でなければならないもの（数値・統計値）→ 構造化参照。**値を埋め込みチャンクから復元してはならない**（近い数字・隣の年の値を返すことは誤答ではなく捏造にあたる） |
| **量** | インフラのみ | データ量・速度はベクトルDBの選定・シャーディング・計算資源で吸収する。**分割境界の理由には決してしない** |

系として導かれる規則：

- **発行主体（団体名・会議体名）は境界ではなくファセット（メタデータ）**。経団連と同友会は同一コーパスに同居する——「各団体の主張の差」こそが核心の質問だから。同様に、審議会議事録コーパスの中で財政審と法制審は会議体ファセットで区別する。
- **同じ機関が複数DBに現れるのは仕様**。財政審の建議（主張文書）は政策主張DB、財政審の議事録（過程文書）は審議会議事録DBに入る。機関は住所ではなくラベルであり、住所を決めるのはジャンル。
- 主張文書と過程文書を同一インデックスに混ぜない根本理由は量ではなく**意味論**：チャンクが代表するもの（機関の立場 vs 会議での個人の発言）、メタデータ（分野タグ vs 発言者・会派・回次）、チャンク単位（意味段落 vs 発言）、引用の作法がすべて異なる。混ぜると双方の検索品質が壊れる。

## 3. 目標のサービス構成

各コーパスを独立のマイクロサービス（MCPツール）として提供する。

| # | サービス | 中身 | 主なファセット |
|---|---|---|---|
| 1 | **政策主張DB**（現行） | 経済団体の提言・意見・要望＋政府の主張系文書（骨太方針・規制改革答申・財政審建議）。将来は**政党の公約・政策集もここ**（新DBではなく新ファセット） | 発行体・分野・日付・文書種別 |
| 2 | **国会議事録DB** | 本会議・委員会の発言記録（国会会議録検索システムAPIが取得元） | 院・委員会・発言者・会派・会期 |
| 3 | **審議会議事録DB** | 財政審・法制審・経済財政諮問会議ほか省庁審議会の議事録・配布資料 | 省庁・会議体・回次・委員 |
| 4 | **地方議会議事録DB** | 都道府県議会＋市区町村議会（両者を分けない。レベルはファセット） | 自治体・レベル・議員・会派 |
| 5 | （欠番・2026-09-04） | 旧「テナント内部DB × n」（特定組織から預かる非公開データ）は本計画の範囲外＝信頼境界の外は作らない（§2）。番号は他文書の参照（#6 統計参照DB 等）を保つため据え置き | — |
| 6 | **統計参照DB** | 政府統計（e-Stat 等の公式API）・日銀時系列・団体統計。**ベクトルDBではなく2層構造**：発見層（どんな統計が存在するかのメタデータ意味検索）＋参照層（値の厳密参照ツール。該当データがなければ「ない」と返す）。評価は hit@5 ではなく**原典との完全一致** | 統計名・調査主体・期間・地域粒度 |
| 7 | （将来）**外国政府DB** | 多言語のため埋め込みモデルが分岐し自然に別サービスになる | 国・機関・言語 |

サービス数は**少なく（5〜8）、ファセットは豊かに**。ツール数の増殖はクライアント側のルーティング品質を劣化させるため、審議会ごと・自治体ごとにサービスを割らない。

**サービスの実装単位（2026-08-15 決定）**：

- **1コーパス＝1プロセス＝1公開ホスト名**の MCP サーバ（`polyarchy-recommendations` / `polyarchy-stats` …）。同一プロセスへの同居や、サーバ側の集約ゲートウェイは採らない（障害分離・独立デプロイ・回帰ゲートの独立性のため）。利用者に1 URL で見せる必要が実証されたら Cloudflare One の MCP server portals を第一候補に検討する（自作しない）。
- **リポジトリ＝Polyarchy 全体**。各コーパスは対象ジャンルを表す名のフォルダに置き、**フォルダ名＝コーパスID**（`corpus` 欄・コレクション接頭辞と一致）：`recommendations/`（政策主張）・`stats/`（統計参照）・将来 `deliberations/`（審議会＝議論・論点）・`diet/`（国会）・`assemblies/`（地方議会）・`foreign/`（外国政府）。名前は対象を表し、機関名・量・技術を含めない。全体名 polyarchy はパッケージ接頭辞（`polyarchy_common`）とサービス名にのみ使う。
- **共通契約は `common/`（`polyarchy_common`）だけに置く**：メタデータ共通コア（層の不変条件）・分野タグ21分類・MCP 入口の作法（ログ／stdio 保護・捕捉ログ・Access JWT・HTTP 定型）。検索スタック・設定・評価はコーパス固有。**あるコーパスの作業セッションは他コーパスのソースを読まない**（把握範囲を1サービスに閉じる）。

## 4. 統合の方式 — 連邦レイヤは作らない

サーバ側にコーパス横断のルーター・統合ランキング層を**実装しない**。

- **ルーティング＝ツールの説明文**。「議会での検討状況を知りたいときは国会議事録DBへ」と書けば、利用者の Claude が質問の文脈で使い分ける。利用者自身の明示指定もできる。利用の実態は「常に全部を見たい」ではなく「いま議会の状況が知りたい」という**意図つきの検索**であり、意図を持つ主体（利用者と Claude）に選択を委ねるのが最も安く正確。
- **統合＝利用者の Claude の言語空間**。コーパスを跨ぐ突き合わせ（提言 vs 国会審議）に欲しい出力は統合ランキングではなく**対置された叙述**であり、それはクライアント側の生成が担う。スコアの比較不能問題（コーパスごとに語彙統計が異なる）はそもそも発生しない。「生成は利用者の Claude 側」という既存の設計思想の延長。
- **コーパス内の横断は例外＝サーバ側に残す**。同一コーパス内の網羅・比較・棄却（例：5団体の主張を漏れなく並べる多段検索）は決定論のコードで実装し、回帰テストのゲート内に置き続ける。クライアント任せにするのはコーパス**間**の使い分けだけ。この線引きにより、守るべき規律（誤答の棄却など）は再現可能なテストで担保され続ける。
- **マクロツールは実証後に opt-in**。特定の型の横断質問でクライアント任せの品質・トークン効率が不足すると観測されたら、その型に限りサーバ側の複合ツールを追加する。統合は「アーキテクチャ」ではなく「必要になった型にだけ足す道具」。
- **統合ロジックの獲得経路（委ねる→観測→型化→ゲート）**。コーパス横断の統合的解釈は当面クライアントの生成AIに委ねるが、これは暫定妥協ではなく**観測フェーズという正規の工程**である。検索クエリの捕捉ログから「主張と統計の突き合わせ」「提言から審議経過の追跡」等の**頻出する統合の型**を特定し、型ごとに引数の固いマクロツール（決定論）と専用評価を実装して自前化する。コーパス内の多段検索（網羅・集約棄却）が実運用の観測から生まれ決定論化された経路と同じ階段を、コーパス間で一段上に登る。統合ロジックは設計するものではなく**実利用から採掘するもの**であり、汎用の統合レイヤは最後まで作らない。

## 5. 現行コーパスの位置づけ（2026-08-11 実データ確認済）

- 現行コレクション（1,249文書・80,632チャンク）は本計画の**政策主張DB**にあたる。うち政府文書28本は骨太方針8・規制改革答申等11・財政審建議9で**全て主張文書**。議事録・議事要旨は含まれておらず、単声/多声の原理に既に適合している（過程文書の収集は審議会議事録DB新設時の仕事）。
- 軽微な例外として団体側に統計資料14本（賃金妥結状況等・全体の約1%）が混在する。実害がなく据え置き。将来「統計DB」を設けるならその際の引っ越し候補。
- 政府文書のファセットは現在 `gov` の一括りだが、発行体別（経済財政諮問会議/規制改革推進会議/財政審）への細分化に必要な情報はカタログに揃っており、メタデータ書き換え＋再取り込みのみで実施可能（新規収集不要）。

## 6. 直近フェーズ（Qdrant 移行）に反映する決定

先回りして連邦を作る必要はないが、**後から変えると高くつく縫い目**が2つあり、次期のベクトルDB移行時に切っておく：

1. **検索アダプタの契約をコーパス単位にする**。`search(corpus, query, filter, k)` を最小契約とし、現行5団体＋政府は単一コーパスとして移行（**団体では割らない**）。以後のコーパス追加は「新コーパスの登録」であり、既存コーパスのインデックスにも回帰テストにも触れない。
2. **メタデータの共通コアを定義する**。全コーパス共通の芯（corpus・発行体・日付・タイトル・出典URL・**公開層**・言語）と、コーパス固有の拡張（発言者・会派・回次等）を分離。特に**層（公開データのみ提供する制約）を共通コアに置き、全コーパスに対する単一の不変条件として維持する**。

## 7. 拡張の順序と遅延事項

| 順 | 対象 | 理由 |
|---|---|---|
| 1 | 審議会議事録 | 取得元が省庁サイトで現行収集の延長。第2コーパスとしてツール分割の型をここで作る |
| 2 | 国会議事録 | 公式APIで構造化済（発言単位・話者・会派つき）。「団体の提言 ↔ 国会での審議」の突き合わせは本サービスの価値が最も立つ接続 |
| 3 | 地方議会議事録 | 価値は大きいが取得・整形コストが支配的（書式が自治体ごとに異なる）。全国一斉ではなく数自治体で型を作ってから広げる |
| 4 | 政党・外国政府 | 政党は政策主張DBへのファセット追加として軽い。外国は多言語埋め込みという別種の投資のため、価値仮説の確認を先行 |
| ※ | 統計参照（最小版） | 主要指標数十個に絞った参照ツールなら審議会DBより小さく作れ、主張↔事実の突き合わせという商品の核を早期に実証できる。**順序への割り込みを検討対象とする** |

**遅延する作業**（実施はコーパス変更・挙動変更を伴うため、回帰テストの再ベースラインと同期して一括で行う。再測定という高価なイベントは2回に集約する）：

- **バッチ1（ベクトルDB移行時）**：政策主張DBへの改名（現「経済団体」名称の実態合わせ）／政府ファセットの発行体別細分化／統計資料の扱いの見直し
- **バッチ2（移行後）**：コーパス内多段検索のMCPツール化（現在は説明文でクライアントの検索手順に委ねている網羅・集約棄却を、サーバ側の決定論ツールとして提供。利用者側のツール呼び出し回数とトークン消費も減る）／返却件数上限の緩和。**多段ツール化を最終土台（移行後）の上で1回だけ行う**ことで再測定の重複を避ける——**実施済（2026-08-28・prod 転写より先行と決定変更）**＝eval 本番経路化（新アンカー 86.9%/0.715）→ `sweep_policy_docs`＋top_k 上限 20 → 再測定 1 回（箱反映・全ゲート PASS）→ Chroma 全廃。経緯は残タスク A2

**触らないもの**：PoC 試行期間中はコーパス・検索挙動を一切変更しない。評価セットには政府文書を正解とする設問が含まれるため、政府文書に関わる変更は評価資産への影響確認を必ず伴う。

## 8. 本計画が却下した代替案（再検討しないための記録）

| 案 | 却下理由 |
|---|---|
| 団体ごとにDBを分割 | 5団体は同一ジャンル・同一スキーマで、「各団体の主張の差」という核心質問の比較対象。分割すると網羅・比較・棄却の機械が回帰テストの外に出て、利用者のツール呼び出しも常時多重化する。得るものがない |
| 会議体ごと・自治体レベルごとにDBを分割 | 同上の縮小版。会議体・レベルはファセットで足りる。ツール数の増殖はルーティングを劣化させる |
| サーバ側の連邦レイヤ（横断ルーター＋統合リランク） | ルーティングは利用者の Claude が説明文から無償で行える。スコア統合はコーパス間で原理的に不能（語彙統計が異なる）だが、叙述による統合なら問題自体が消える。§4 の通り必要が実証された型にだけマクロツールを足す |
| 量を理由にした分割 | 量はベクトルDB・シャーディング・計算資源の問題。境界は意味（単声/多声・比較可能性・信頼境界）でのみ決める |
