> 読み方の注（2026-09-19）＝§1〜§6 は 2026-08 の試行期間当時の前提（索引は v5/Chroma・試行の実トラフィックが staging に来ている）で書かれている。

## 1. 現状認識と原則

- PoC の実トラフィックは staging の EC2 に来ている。専用 prod はまだ無く、**試行中はこの箱が事実上の本番**である。
- 箱にコードが届く経路は、operator が手動で deploy 系スクリプトを実行したときのみ（CI/CD は存在しない・箱は git を見ていない）。したがって隔離は物理的に既に成立している。
- 原則：**箱を凍結し、開発はローカルで進め、昇格は試行後にゲート経由の一方通行で行う**。

```
開発ループ（毎日）   ＝ Mac：Qdrant(Docker)＋v5複製＋回帰ゲート4種 → 完全ローカル・クレジット0
検証チェックポイント ＝ 使い捨てEC2：本番同等条件の性能・メモリ実測 → 終わったら停止
試行環境（凍結）     ＝ staging EC2：deploy 系スクリプトを向けない
```

---

## 2. 凍結ルール（試行終了まで）

**唯一の必須ルール：試行環境に対して `deploy.sh`・`rollback.sh`・`cloudflare-guard.sh` を実行しない。**

補強（いずれも repo 側のみの作業・箱には触れない）：

1. **FREEZE ガード**：`deploy/FREEZE` ファイルが存在する間、`deploy.sh` は冒頭で中止する（誤操作・AI セッションの誤実行対策）。試行終了時にファイルを消して解除。
2. **配信中コミットのタグ**：箱に載っている code tar に対応するコミットへタグ（例 `trial-YYYY-MM`）を打つ。障害時の緊急修正は**このタグから hotfix ブランチ**を切り、開発中の変更を巻き込まず最小差分で直して deploy する（凍結の唯一の例外＝障害対応）。
3. 箱への SSM 接続は**読み取り調査のみ**可。依存更新・再起動・設定変更は障害対応を除き行わない。
4. 開発途中の変更を導入団体に見せる必要がない間は **push しない**（ローカルコミットは公開されない。git から切り離す必要はない——切り離しても安全は増えず、再統合の手間だけ増える）。

## 3. ローカル開発環境（Mac）

脱PC によって Mac のフルスタックは配信義務から解放されており、そのまま開発環境として使う。
複製フォルダは作らない（本作業フォルダでそのまま開発する）。

- 揃っているもの：conda env `polyarchy`・v5 データ（Chroma 80,632チャンク）・回帰ゲート4種（クレジット0）・全スクリプト。
- **Qdrant は Docker でローカルに立てる**。規模の目安：v5 のベクトル実体 ≈ 250MB、180k 拡大時 ≈ 550MB・常用メモリ数GB＝Mac で十分。追加10万チャンクの埋め込み計算（ruri/MPS）は数時間〜一晩の一回きり。
- in-memory BM25 の 180k 破綻問題は、Phase B で BM25 を Qdrant 側（sparse/全文）へ移すこと自体が解であり、ローカル開発はその解消側を実装する。
- **判定は常に回帰ゲート**：`--retrieval-only` / `--filter-eval` / `multistage_eval` / `mcp_smoke`。アダプタ差し替えの受け入れ基準は既存アンカーとのバイト一致（意図的な挙動変更はバッチとして別途再ベースライン）。

ローカルでできないのは2つだけ：①本番同等条件（t3.xlarge/Linux/メモリ上限）での性能実測 → §4、②数百万チャンク級の将来コーパス → 該当フェーズで別途設計。

---

## 4. 使い捨て検証 EC2

性能・メモリの実測が必要な節目だけ、dev 用インスタンスを立てて使い、終わったら停止する。

- `deploy/env/` に **dev 用 env を追加**し、試行環境とは**別インスタンス・別 tfstate・別 S3 プレフィックス**で完全分離する（凍結ルールと両立）。
- コスト：使う日だけ起動（停止中は EBS のみ ≈ 月数ドル）。常設の第2環境は作らない。
- 用途例：Qdrant 移行後の latency/常駐メモリ実測、ingest の実時間確認、systemd unit の動作確認。

---

## 5. データの流れ（接点は一方通行のみ）

```
試行EC2 ──(毎時 fuelsync)──▶ S3 ──(読むだけ)──▶ Mac の開発・分析
```

- 開発側から箱・箱のデータへ**書き込む経路を作らない**。
- 捕捉ログの分析（docstring 従順性の観測・週次トリアージ）は **S3 側の複製**に対して行う。ログは30日で消えるため、トリアージは30日以内に回す。
- eval への追記はローカル資産（配信は eval を読まないため試行に影響しない）。

## 7. 出口 — この規約は昇格パイプラインの雛形

試行の窮屈さの根本原因は staging と本番が同一の箱であること。導入団体 AWS への prod 移設が済めば、実トラフィックは prod へ移り、自分の箱は本来の staging に戻る。本書の「凍結 → タグ → hotfix → ゲート → 昇格」は 2 週間しのぎではなく、**prod 運用時の昇格パイプラインとしてそのまま持ち上げる**。

持ち上げ先＝**CI 化**（[運用設計.md](運用設計.md) §2.5）：ゲートを公開リポジトリの PR／main に紐づけ、release も CI から行い、
staging→prod の昇格を同じ成果物で行う。§1 の「箱にコードが届く経路は operator の手動実行のみ」は CI 化で「main マージ → CI → S3 → 箱の自動適用」に置き換わる（箱側の自動適用・切り戻しは無変更）。
