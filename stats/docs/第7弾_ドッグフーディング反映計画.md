## 0. 結論（先に）

1. **最優先はデータ拡充ではなくサービスの欠陥修正**。「該当が無ければ『ない』と返す」がこの DB の核の約束だが、
   **正しくない『ない』を 3 系統で返していた**（§2 の S-1〜S-3）。うち 2 つは今回の利用者が実際に踏み、設計書に誤った改訂を入れかけている。
   要望 D-3 の探索コストも、原因は「土地が無い」ことではなく S-3（ヒントが的外れ）だった。
2. **D-1 は要望の前提が誤っている**。制度部門別（非金融法人・金融・一般政府・家計・NPISH）の**付加価値は JSNA では公表されていない**
   （所得の発生勘定は一国経済のみ＝原典で確認）。代わりに**付表 2「経済活動別の国内総生産・要素所得」**が、利用者の目的（κ の分解）に対して
   より直接的な材料を持つ（産業 17 分類 × 産出額/中間投入/GDP/固定資本減耗/生産税/雇用者報酬/営業余剰＋**（参考）制度部門別 3 区分**）。
3. **D-2 は実測で「できる」**。OECD SDBS に**日本が入っている**（2021 年・全産業・全規模の企業数 3,445,142、従業者規模 11 区分）。
   同じ表に付加価値（VAFC）もあるため、**D-6 の「規模区分の軸が違うから並べられない」という障害は大幅に緩む**（OECD 側が日本を従業者規模で載せている）。
4. D-4（OECD STAN／BEA）・D-5（EU KLEMS）は据え置き。段 C の SNA 産業別を入れてからでないと日本側の受け皿が無い。

## 2. ログから見つかった欠陥（要望に無い・優先度は最上位）

### S-1 `find_statistics` の複数語クエリが常に 0 件（**偽の「ない」**）★最重要

`core/registry.py:222` の照合は `q in primary` ＝**クエリ文字列まるごとの部分一致**。空白区切りの語は一切分解されない。

実測（2026-08-22 のログにある 3 本のうち 2 本が偽陰性）：

| クエリ | 実際の返り | 語を 1 つにすると |
|---|---|---|
| `固定資本減耗 雇用者報酬 営業余剰 純付加価値`（dataset=sna2020） | **0 件** | 固定資本減耗 34 件・雇用者報酬 3 件 |
| `産業連関表 投入係数 中間投入 商業マージン` | 0 件 | （収録は無いが、原典には付表 4/5/5-2 がある＝§1.2） |
| `介護報酬 診療報酬 介護 医療 公定価格` | 0 件 | 0 件（これは正しい 0） |

利用者は 0 件を見て**空クエリで 40 件を総なめする**という迂回をしている（12:39:30）。この DB は「無ければ無いと返す」ことを売りにしている以上、
**偽の 0 は最も高くつく欠陥**。修正：

- 照合を**空白区切りトークンの AND**にする（全トークンがどこかに当たれば該当）。強度は「全トークンが primary に当たる > 一部が notes/表名」で決定的順序を保つ。
- **0 件のときにヒントを返す**：`matched_tokens`（語ごとの単独該当数）と `hint`＝「『雇用者報酬』は 3 件該当。語を減らして再検索」。
  **語を減らせば当たると分かる 0** と、**本当に無い 0** を利用者が区別できることが要件。
- 正規化（全角/半角・カタカナ長音・「業種」等の助詞は対象外）は最小に留める（決定的順序を壊さない範囲）。

### S-2 目録の無言切り捨て（＝所見 §5.1）

上記のとおり。**目録は「無いことの根拠」に使われる**（利用者はそう使い、誤った改訂を入れかけた）。
「利用側に『目録を根拠に使うな』と要求するのは筋が悪い」という所見に同意する。修正：

- `measures` は**全件返す**（hojin 46・sna2020 66。文字数は微々たるもの）。
- 上限を設ける場合は必ず `measures_truncated: true` ＋ 全件数を返す（`find_statistics` の `truncated` と同じ扱い）。
- `units[:6]`・`example_series[:4]` も同じ規則に揃える。
- **回帰ゲート**：「目録に出る measure 集合 ⊇ レジストリの measure 集合」を全 dataset で機械検証（§4）。

### S-3 `lookup_panel` が展開 0 件のとき**診断を捨てて的外れなヒントを返す**

`serving/mcp_server.py:336` で `_expand_pattern` は `dim_errors`（＝どの dim のどの slug に登録系列が無いか）を正しく計算しているのに、
`ids` が空になると `:340` の早期 return がそれを**丸ごと捨てる**。実測：

```
lookup_panel(id_pattern="mof.hojin.land.{industry}-{size}.fy", dims={industry:[mfg_food,ict], size:[cap1b]})
→ {"found": false, "reason": "no_series",
    "hint": "series_ids か id_pattern（＋dims）を指定してください。…"}   ← 指定している
```

利用者は 10:14 に `fixed_assets`、10:15 に `land` でこれを踏み、`find_statistics("資産", dataset=hojin)` へ迂回してから `tangible_fixed_assets` に辿り着いている。
修正：

- `ids` が空でも `errors: dim_errors` を必ず返す。
- `hint` を状況別に分ける。**「その measure は収録済みだが dims が違う」場合は、収録済みの組合せを列挙する**
  （例：「`land` の収録は `allexfin-allsize` のみ」）。`_expand_pattern` は `seen_slugs` を既に持っているので追加コストは無い。
- `lookup_statistic` の `unknown_series` にも同じ情報を載せる（現状は一般的な ID 規則の説明のみ）。

## 5. 順序と理由

```
段 A（S-1 → S-3 → S-2 → A-4） → 段 B（B-1/B-2 → B-3） → 段 C（C-1/C-2 → C-4/C-5） → 段 D 再評価
```

- **段 A が先**の理由：段 B・C で系列を増やすほど、偽の 0 件と切り捨てられた目録の害が増える。器を直してから中身を足す。
- **段 B が段 C より先**の理由：既存の accessor で完結する（新規パーサ不要）＝短い。D-2 は「必要条件 1,902 社／兆円」に国際的な参照点を与える項目で、利用者の討議資料に直接効く。
- **段 C は accessor 追加を伴う**ので独立した段にする。D-1 の回答（＝非公表の明示）は C-5 で確定させる。
