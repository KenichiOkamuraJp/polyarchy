# EDINET XBRL 正規化検証（企業情報アプリ 着手前検証）

> **状態：記録（検証結果・2026-08-22。更新しない）。**

分類：記録（検証結果）／版：2026-08-22／対象：`edinet/verify_xbrl.py`

## 0. 結論（先に）
- **法的前提はクリア**：EDINET 利用規約（令和7年4月25日改訂）＝公共データ利用規約 PDL1.0（CC BY 4.0 互換）。商用利用・再配布・翻案可、出典明記＋加工明記が条件、API 利用はスクレイピング禁止の例外。規約対象外＝EDINET タクソノミ等（値・要素名の利用は可、タクソノミ自体の再配布は避ける）。第三者権利条項があるため**原文丸ごと再配布ではなく引用 1 行＋出典 URL 方式**（polyarchy の型）が適合。
- **数表の正規化は「主要な経営指標等の推移」要素で業種横断に取れる見込み**：金融庁公式サンプル（有報 J-GAAP 版・IFRS 版）で 12 項目（売上高・経常利益・親会社帰属純利益・純資産・総資産・自己資本比率・ROE・従業員数 連結/単体・平均年間給与・平均年齢・平均勤続年数）を全て取得。IFRS は要素名が `…IFRSSummaryOfBusinessResults` に変わるので別名表で吸収する。
- **定性開示は TextBlock 要素で丸ごと取れる**：事業の内容・経営方針・サステナビリティ・事業等のリスク・MD&A・大株主・役員の 7 ブロックを確認。context は財務の `CurrentYear*` ではなく **`FilingDateInstant`（提出日時点）**。
- 実データ 10 社の検証は **EDINET API キー待ち**（本人登録が必要＝利用申請ページから。無料）。キーは `EDINET_API_KEY`（環境変数か `edinet/.env`・git 外）。

## 1. 仕様として確定したこと
| 論点 | 結果 |
|---|---|
| API | v2・全エンドポイントに `Subscription-Key` 必須。書類一覧 `documents.json?date=YYYY-MM-DD&type=2`、本体 `documents/{docID}?type=1`（XBRL zip） |
| 有報の判定 | `ordinanceCode=010`（開示府令）× `formCode=030000`（有報）× `xbrlFlag=1`。訂正有報は別様式 |
| インスタンス | zip 内 `XBRL/PublicDoc/jpcrp030000-asr-*.xbrl` が 1 個（Inline XBRL の .htm とは別に素の XBRL がある） |
| context ID | EDINET が固定：`CurrentYearDuration/Instant`・`Prior1YearDuration`…・`_NonConsolidatedMember` 接尾で単体・`FilingDateInstant` |
| 会計基準 | `jpdei_cor:AccountingStandardsDEI`（"Japan GAAP" / "IFRS" / "US GAAP"） |
| 連結有無 | `jpdei_cor:WhetherConsolidatedFinancialStatementsArePreparedDEI`。連結なしの社は `_NonConsolidatedMember` へフォールバック |
| 比率 | `unitRef=pure`・小数（0.444＝44.4%）。公表どおりの文字列で保持し換算しない（stats と同じ原則） |
| 金額 | `unitRef=JPY`・`decimals=-6`（百万円単位で公表された値を円で表現）。decimals も保持 |

## 2. 別名表（業種横断の正規化キー → XBRL 要素）
`verify_xbrl.py` の `TARGET_NUMERIC` が正。サンプルで確認したのは J-GAAP 一般事業会社と IFRS の 2 型。**未確認＝銀行（OrdinaryIncomeBNK）・証券（OperatingRevenueSEC）・保険・建設・鉄道など業種別様式**。実データ検証ではこれらを必ず含める（coverage.md の「未採用の Summary 要素」一覧から別名を足す）。

## 3. 実データ検証（キー入手後）の手順
```
export EDINET_API_KEY=...
python -m edinet.verify_xbrl --from 2025-06-20 --to 2025-06-30 --n 10      # 3 月決算の提出集中期
```
出力 `edinet/data/verify/<日付>/coverage.md`。見るもの：
1. 12 項目×7 ブロックの被覆率（目標：一般事業会社で 100%、金融で別名追加後 100%）
2. 「未採用の Summary 要素」＝別名表に足す候補
3. 10 社の内訳に **銀行 1・証券 1・保険 1・IFRS 2・連結なし 1** を意図的に含める（`--docids` で指定可）

## 4. 次に決めること（設計）
- **数表の保持形**：stats 型（系列＝企業×項目、期間＝年度、値＝文字列、出典＝docID URL＋要素名＋context）。「厳密参照」がそのまま使える。5 期分の推移が 1 書類に入っているので、最新の有報 1 本で 5 年が埋まる。
- **定性開示の保持形**：TextBlock は HTML。テキスト化して章単位で claims 型（ベクトル＋BM25）。大株主・役員は表＝構造化（HTML table パース）して stats 型にもできる。
- **規模**：上場約 3,900 社 × 有報 1 本/年。数表は DuckDB/Parquet で数 GB・RAM 不要。ベクトルは直近 2 期の 3〜4 ブロックに限定すれば数百万チャンク→量子化で RAM 数 GB。32GB 級の VPS 1 台で stats と同居可。
- **出典表示**：各値に「出典：EDINET（https://disclosure2dl.edinet-fsa.go.jp/… docID）、PDL1.0／polyarchy が XBRL から抽出・加工」。license 区分＝○。
- **レート**：規約「短時間における大量のアクセス」禁止＝1 req/秒・日次差分取得（提出日で一覧→新規 docID のみ取得）。初回全量は 3,900 zip（各 1〜5MB）＝数時間。
